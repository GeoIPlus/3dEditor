# 3D-69 checkpoint

Goal: a point cloud in another horizontal CRS than the building (typically a geographic-CRS building, EPSG:4937, and a
UTM cloud, EPSG:25832) is reprojected on the server into the building's LOCAL frame, so that `FIT_PLANE` and the
heatmap give the all-UTM results (D-164). The cloud CRS comes from the context, never from the file (D-165).

## Findings of the read phase (facts, [V] = verified in the file)

1. [V] `services/kernel/src/cloud-points.js` maps LOCAL <-> world with the public `worldToLocal` / `localToWorld`,
   which use `brep.localFrame(frame)` with the default **translation** mapping (projected CRS only). For a geographic
   building this is wrong today (degrees minus a degree origin, no ENU), not only for a foreign cloud CRS.
2. [V] The `crs` table (`src/crs/epsg-table.json`, 110 kB) holds for projected CRSs **only the axis order** (4262
   entries): no base geographic CRS, datum or projection parameters. A UTM -> geodetic inverse is therefore not
   possible from the table today; `tools/crs-table/generate.mjs` must also write the projection (method + parameters)
   and the base geographic CRS / datum of each supported projected CRS. `proj.db` is reachable (pyproj 3.8.0 wheel
   downloaded 2026-11-24, as in tools/crs-table/README.md).
3. [V] `createMetricFrame` (geographic) = proj4 geodetic -> geocentric + topocentric rotation; heights as in the file
   (D-93). The same path serves cloud points once they are geodetic on the building's datum.
4. [V] Fixture pair exists: GT-I1 in EPSG:25832 and `packages/geo-model3d/test/crs/fixtures/gt-i1-epsg4937.cityjson.json`
   (made by `make-fixture.mjs` with proj4's UTM inverse). EPSG:25832 and EPSG:4937 share the datum ETRS89 (EPSG:6258),
   so the accept pair needs no datum shift.
5. [V] The points port and adapters are 3D-70's files (parallel session): the port stays "world box in the dataset
   CRS"; the cloud CRS is carried beside the port, not in it.
6. [V] Contracts today carry no cloud CRS: `heatmap-request` v1 and `command-payload-fit-plane` v1 have the LOCAL
   `PointSelection` only; the CP 3DQM extension (with its `dataset` member, Q-03 answer) is an SC schema of 3D-43
   (`proposed`), not in this repository.
7. Local frames differ between the two cases (UTM grid: translation, grid north, scale 0.9996..; ENU: true north,
   true metres). "Same result" is therefore compared frame-independently: heatmap per-face signed distances (scalars)
   and the fitted plane mapped to one common frame (distance of the two planes at the selection's points).

Design (revised after the owner's answers D-3D69-1..3, 2026-11-24):
- Built as below, with two changes: projections come from PROJ's own proj-strings (pyproj 3.8.0 = PROJ 9.8.1, the
  wheel that also supplies `proj.db`), not from hand-mapped EPSG parameters; the composition with the rotation lives in
  `src/index.js` (`check:arch`: root files may not import each other; no DAG change, `tools/check-arch` untouched).
- `crs` (kernel): table gains, per supported projected CRS, `{ order, base, method, params }`; new
  `createCrsMapping(fromRef, toRef)` -> `{ identity, forward(p), inverse(p) }` world(from) <-> world(to), via geodetic on
  the shared datum (proj4 with explicit parameters, no `+nadgrids`, no `+towgs84`). Heights pass through. Table also
  records the datum code of every geographic and projected CRS; different datums -> `INVALID_CRS` naming both (D-3D69-2).
  Projection methods: every EPSG method proj4 2.23.0 implements and the generator can map (D-3D69-3); first step is an
  inventory of `proj.db` method codes x proj4 projections, each mapped method checked against an oracle (pyproj/PROJ
  values computed offline and written into the test as numbers, as 3D-32 did); unmapped methods -> `INVALID_CRS`.
- kernel public API (new entries, names to be recorded in the module card): `cloudToLocal(frame, cloudCrs, points)`
  and `localBoxToCloud(frame, cloudCrs, box)`; they compose `createCrsMapping` with the building's real metric frame
  (`createMetricFrame` for geographic, translation for projected) and `localFrame` rotation. Same CRS -> today's path.
- `services/kernel/src/cloud-points.js`: `readLocalPoints(port, frame, sel, { cloudCrs })`; world box from the 8 local
  corners mapped to the cloud CRS plus a z pad for earth curvature over the box (half-diagonal^2 / 2R, derived, not a
  tolerance); exact filter stays in the kernel.
- Cloud CRS enters as a service-side dataset descriptor `{ port, horizontalCrs }` (D-3D69-1): no model3d schema change;
  3D-43 (SC) must carry the CRS in the extension `dataset` member -> intake / mirror note at finish.
- Size: D-3D69-3 widens the projection work beyond the accept case; if the method inventory shows the WP outgrows M,
  propose a split via intake (e.g. TM + accept first, other methods as a follow-up row) before building it.
