## 2. CP and DP roles

### 2.1 Control plane = `backend/` (Python, FastAPI, PostgreSQL)

- The requirement: when an operator takes a block, "THE control plane SHALL form an Operaflow document for it ...
  and SHALL publish it at an address of the platform's own" (`CS docs/specifications/functional-requirements.md:547`);
  validate it with its own validator held to the format's suite, sign it, keep its bytes, serve the territory to the
  document's token, receive progress and stops (`:549-556`). Stages 1-4 of the Operaflow walkthrough are implemented;
  stage 5 (delivery record) and 6 (acceptance) are not (`:558`).
- Code: the document is built in `CS backend/src/crowdsource_backend/services/operaflow_documents.py:540-645`
  (`formatVersion`, signed `issuer` with key-set address, `open`, `data`, `access`, `work`, `progress`, `issues`).
  The pinned format is `FORMAT_VERSION = "1.0.0-rc.1"` (`CS backend/src/crowdsource_backend/operaflow/validator.py:61`),
  the reference copy is the rc.1 tag, commit `d7a98bb` (`CS reference/operaflow/manifest.json`; the root
  `CS README.md:97` still says `1.0.0-alpha.4`, stale there).
- Persisted CP state: tables `operaflow_document`, `operaflow_progress_record`, `operaflow_issue`,
  `operaflow_answer`, `block`, `block_history` (`CS backend/src/crowdsource_backend/models.py:1245, 1287, 1324, 1380,
  1424, 1463`).
- Only 2D mapping gets documents: `if project.project_type != ProjectType.MAPPING_2D: ... its blocks are given no
  document` (`operaflow_documents.py:663-664`); the only project type is `MAPPING_2D = "2d_mapping"`
  (`CS backend/src/crowdsource_backend/schemas.py:780-785`).
- The editor is outside the platform: "THE platform SHALL NOT contain the seamline editor: the editor is an
  application of its own, which opens the block's Operaflow document" (`functional-requirements.md:95`). Who builds it
  is open there (`CS docs/artifacts/decisions/open-questions.md:377`, O-360). This is the same role 3DQM would play
  (a Tools-Plane application opening an issued document).

### 2.2 Data plane = `streaming/` + worker + object store

- Requirement: bulk data "through a data-streaming service separate from the central metadata service"; the bulk-data
  plane (object storage, processing pipelines, streaming service) is "one deployable unit", placed in the platform's
  account, a customer's account or customer infrastructure (`functional-requirements.md:418-421`, FR-27). Two stores per
  project, exchange and system; operators never reach a store, only the streaming service (`:426-427`). Registration,
  handshake and an outbound-only channel to the CP (FR-28, `:436-455`).
- Code: `CS streaming/README.md:1-50` lists the service: token check (`src/token.rs`), files (`src/files.rs`),
  dataset guard (`src/datasets.rs`), OGC API (`src/ogc/`), worker relay (`src/worker.rs`), store (`src/store.rs`),
  keys, registration, poll, commands, signing.
- Pipelines run in the worker, the backend's image in a second role (`CS docs/artifacts/architecture/deployment.md:217`).
  Present pipelines: `prepare_2d`, `ortho_dataset`, `oblique_dataset`, `grid`, `las_class_reset`
  (`CS backend/src/crowdsource_backend/pipelines/`). `las-class-reset/1` only sets every LAS point's class to 0
  (`pipelines/las_class_reset.py:1-24`); it is an early pipeline test, not a point-cloud service.

### 2.3 Relation to the Operaflow format

- CS is a **producer and consumer of Operaflow documents**: issuer (CP role), dataset server (DP role), progress
  receiver. Operaflow stays the format; CS is one implementation. This matches 3D-01 §9.1 (roles, not code, in the
  Operaflow repository).
- Version alignment: CS pins `1.0.0-rc.1` (`validator.py:61`). 3D-01 read Operaflow at `608a824`; SC pins
  `cf08a35` (3D-01 §9.3). Three different pins of one format; 3D-27/3D-06 must fix one for 3DQM.

## 3. How datasets are served

### 3.1 Forms CS puts into documents
From `operaflow_documents.py:581-607`:

| Document key | `form` | `reach.by` | Address |
|---|---|---|---|
| `ortho` | `ogc-api-tiles` | `stream` | `{dp}/ogc/{project}.ortho/collections/images` |
| `seamlines` | `ogc-api-features` | `stream` | `{dp}/ogc/{project}.ortho/collections/seamlines` |
| `territory` | `geojson` | `location` + `digestSRI` | `{cp}/.../documents/{id}/territory` |

There is no `progress.save` member in the document (`:640-645`): results are written into the `seamlines` stream
dataset itself (§4).

### 3.2 Dataset kinds on the DP
- `pub const KINDS: [&str; 2] = ["ortho", "oblique"];` (`CS streaming/src/datasets.rs:70`); any other kind is
  refused (`:119`). FR-32..FR-34 define the OGC API interface and exactly these two datasets
  (`functional-requirements.md:503-541`): rasters as COG tiles by one ranged read, footprints via FlatGeobuf R-tree,
  seamlines as an OGC API Features layer, the only writable layer.
- A grep of `*.rs`, `*.py`, `*.ts` for `copc`, `ept`, `cityjson`, `laz` finds only `las_class_reset.py` (run at
  `aa71c6e`). No phase-2 step, open question or user story names a point-cloud, CityJSON or building dataset (grep of
  `phase-2-plan.md`, `open-questions.md`, `mvp-user-stories.md` for `copc|cityjson|3d tiles|building|lidar dataset`:
  no relevant hit).

### 3.3 Point clouds and box reads (Q-05)
- Raw project files: `GET /projects/{project_id}/files/{*key}` returns a file "or the range of it a `Range` header
  names" (`CS streaming/src/files.rs:8, 250-312`), backed by S3 ranged reads (`CS streaming/src/store.rs:286-309`).
  Each call asks the CP for `read`/`write` permission first (`files.rs:116-160`). So a COPC file stored as a project
  file **could** be read in parts by a COPC-aware client, but: (a) it is not an Operaflow dataset CS puts into any
  document; (b) there is no server-side box query; (c) files of a dataset path are refused on this route
  (`files.rs:86`, `not_a_dataset`).
- The `engine/` point-cloud renderer is a spike with its own octree node format (`CS engine/README.md:1-9`,
  `engine/src/transport.ts:29-31` fetches `/nodes/{name}.bin`); it is not served by the DP.
- Conclusion: **the DP does not serve point clouds as `copc`/`ept` by `stream`, and has no box read.** For the kernel
  service to read points by box from CS, CS would need a new dataset kind (FR + step in CS), or 3DQM reads COPC by
  range from the files route (not an Operaflow dataset; outside the format).

So CS gives 3DQM a pattern (optimistic locking with ETag/`If-Match`, as Operaflow `progress.md:26-36` requires), not a
place. Q-02 for building models remains 3DQM's own unless CS adds a dataset kind for CityJSON.

## 5. Auth

- Identity: Keycloak locally, Amazon Cognito as target, over OIDC (`deployment.md:74, 233`;
  `CS docs/artifacts/architecture-summary.md` row "Identity").
- DP: the caller's token is checked against the provider's discovery document and `jwks_uri`
  (`CS streaming/src/token.rs:8-10, 112-116`), then the CP's permission route is asked with the caller's token, signed
  by the DP's key; given permissions are cached 120 s (`CS streaming/src/permission.rs:166-187`; FR-27
  `functional-requirements.md:430`).
- Documents: `access.grants` = an OAuth token for `ortho`+`seamlines` (authorize/token endpoints, client id, optional
  redirect: code flow for an interactive app), a bearer secret for `territory`, and a `send` token for progress
  (`operaflow_documents.py:546-552, 609-638`).
- **No `client_credentials` grant** appears in `backend/src`, `streaming/src`, `infra/src`, `local/` (grep, 0 files).
  Operaflow requires a server to use the client-credentials grant (`data-and-access.md:42`, 3D-01 §9.3 B). A 3DQM
  kernel service reading CS datasets itself therefore has no supported path today; reading on behalf of the operator
  (token passed from the client) is the only one that exists. [V] for absence; whether CS would add it is unknown.
- CP <-> DP: RFC 9421 HTTP message signatures, Ed25519, both directions (`streaming/README.md` `src/signature.rs`,
  `src/signing.rs`).

## 6. Deployment

- Target AWS, CP in eu-central-1 on ECS Fargate (1 task, ARM64, 0.5 vCPU, 1 GB), Aurora/PostgreSQL, Cognito, CDK in
  `infra/` (`deployment.md:40-76, 232`). Each public DP: one Fargate task, streaming + worker containers
  (`deployment.md:87, 217-218`). Customer DPs: Docker, deployed by the Windows desktop client (FR-31,
  `functional-requirements.md:484-501`).
- State: an environment `dev` is deployed and destroyed per step; nothing runs permanently
  (`CS docs/artifacts/plans/phase-2-plan.md:3, 195`). [V]
- For Q-14 / D-33: the DP is a fixed set of containers (streaming, worker) plus pipelines in the backend image. There
  is no slot for a third-party service container; adding the 3DQM kernel service there needs a CS requirement
  (FR-27 places pipelines "unchanged" in the DP, `functional-requirements.md:434`) and CS's own process (principal
  approval per its `CLAUDE.md`). Its stack is Python + Rust; the kernel is JS (Q-01 open).

## 7. D-32 - verdict

**Corrected, partly confirmed.**
- Confirmed: CS is a real implementation of the Operaflow CP role (issuer, signer, progress/issue receiver) and DP role
  (dataset server with token + permission checks, optimistic-locked writes), pinned to `1.0.0-rc.1`. [V] §2
- Corrected: "everything should be there" does not hold for 3DQM at `aa71c6e`. CS serves only 2D mapping (one project
  type, two raster/vector dataset kinds), issues documents only for `2d_mapping` projects, has no point-cloud stream,
  no box reads, no CityJSON or building dataset, no store for building versions/journals, and no server
  (client-credentials) grant. [V] §3-§5
- Consequence for 3DQM (to be decided by 3D-02/3D-03, not here): either CS grows a 3D project type with point-cloud
  (COPC by `stream`) and CityJSON datasets (CS-side work under its process), or 3DQM's CP/DP role for 3D data is
  served elsewhere. Which is the owner's choice.
