9. **Operaflow holds no Data Plane implementation.** D-30 names it the DP, but the repository is the format and its

   provider's datasets live, plus 3DQM's own store for what the format does not carry.

## 6. Operaflow (CP) - workplace contract, assignment, roles, planes

### 6.1 What it is
A **format/specification repository**: "the definition of the exchange document that an application reads"
(`OF format/README.md:6`); reference validator, application and conformance suite, no deployed service. Not published:
release candidate `1.0.0-rc.1` (`format/README.md:29`). SC pins an earlier revision `cf08a35` (`SC docs/sources.md:12`).

### 6.2 Document shape
Required only `formatVersion`, `id`, `issuer` (`format/schema/exchange-document.schema.json:7`). Optional parts
(`format/specification/README.md:37-56`): `open` (project, layers, view, tools, operator), `data` (datasets by key),
`access`, `work` (scope, territory, units, method), `requirements` (items, sampling, results), `checklist`, `progress`,
`links`, `issues`, `acceptance`, `next`, `offline`, `extensions`.

### 6.3 Extensions
Keyed by absolute URI (`schema:2779-2790`); the URI path names the content and **never a product**
(`format/specification/extensions.md:9-10`; decision `docs/artifacts/decisions/decision-log.md:2964-2966`, D-311). SC follows
the same rule (`SC docs/decisions/DECISIONS.md:39`, D-22). The OrthoQM payload is `extension-orthoqm.schema.json` in SC with 13
required members (`SC contracts/extension-orthoqm.schema.json:8`): `profile`, `intent`, `contractId`, `contractRevision`,
`issuedAt`, `expiresAt`, `assignment {id, userId, leaseRef, leaseEpoch, deadline}` (`:16`), `productionUnit`,
`dataset {manifestUri, manifestSha256, baseline, ...}`, `production`, `rendering`,
`runtime {sessionExchangeEndpoint, assetEndpoint, editEndpoint?, progressEndpoint, defectEndpoint, resultEndpoint,
credentialMode, contractTrust}` (`:143`), `deliverable`. This is the model for the 3DQM extension (Q-03).

### 6.4 Work, assignment, roles
- One document is for one operator: `open.operator {id, role}`, role is "as the issuer names it" (`open.md:32`, `:111-112`).
- Units are given exactly one way: `list`, `from` (features of a dataset), or `grid` (`work.md:11`). Buildings can be
  units via `from` over a CityJSON dataset or `list` with `feature` ids (inference).
- No multi-person assignment, no role vocabulary, **no separation-of-duties rule**. Acceptance is a separate document
  with a `verdict`, linked by `links` (`links-and-issues.md:96-98`). D-09's "different person approves" is ours to enforce
  (compare the operator id of the production document and the acceptance issuer), or the issuer's.
- Closest examples: `format/examples/uc-10-roofs-contract.valid.json` (LAZ cloud `:44`, result `form: "cityjson"` `:60`,
  requirement `rmse-horizontal` limit 0.2 `:105-109`, `progress.save`) and `uc-08-model-checklist.valid.json`
  (QC of a 3D model, `operator.role: "reviewer"` `:32`, `checklist[]`).

### 6.5 Data, saving, history
- Dataset: `id`, `version`, `form`, `reach{by,href,...}`, `crs`, `digestSRI` (`data-and-access.md:72-83`); `by` is
  `location` (whole), `stream` (in parts) or `package` (`:95`); forms include `cityjson`, `las`, `laz`, `copc`, `ept`
  (`:77`); access enforcement sits with the data provider (`:24`).
- Saving: results go to the datasets in `progress.save` (`progress.md:25`); a `location` dataset is saved by whole-body
  `PUT` with `If-Match` (`:26-30`); OGC API Features Part 4 per feature (`:31-32`). Delivered bytes are immutable and
  referenced by digest (`acceptance.md:20`); otherwise "a store of its own, at an `https` address" (`acceptance.md:17`).
- **No edit journal, history or retention** in the format (searched; not found).

### 6.6 Planes
"The Atlas's three planes are read as roles ... Control the issuer, Data the data provider, Tools the supporting
application ... no field names a plane" (`decision-log.md:1138-1144`, D-98). Hits: "data plane" 106, "tools plane" 20,
"3dqm"/"lidarqm" 0. Operaflow itself names no DP or Tools Plane repository (the owner did: D-30, D-31) and says nothing about where a tool's server side runs.

## 9. Operaflow as CP + DP: data, point clouds, conformance (D-30, D-31, Q-15)

### 9.1 What "Operaflow = DP" means in code
- The repository holds the format (`format/schema`, `format/specification`), a reference validator
  (`format/validator/`), a headless reference application (`format/application/README.md:4`: "a headless supporting
  application that carries out the rules ... so that each can be tested"), a compatibility gate (`format/compat/`), the
  conformance suite (`format/suite/1.0.0-rc.1/`) and method tooling (`tools/`). There is no data service, no storage and
  no server code.
- The format reads the planes as roles: "Control the issuer, Data the data provider, Tools the supporting application"
  (`docs/artifacts/decisions/decision-log.md:1138-1144`, D-98). "What passes between the two planes is the platform's
  own, and the format says nothing about it" (`format/walkthrough.md:24`). Access is enforced by the data provider
  (`format/specification/data-and-access.md:24`).
- So for 3DQM: CP = whoever issues Operaflow documents. DP = whoever serves the datasets those documents address
  (`https` only, `data-and-access.md:23`). The kernel service is a part of the 3DQM **supporting application**.

### 9.2 Point-cloud access (Q-05)
- A dataset names its `form` (`cityjson`, `las`, `laz`, `copc`, `ept`, ...; `data-and-access.md:77`) and its `reach.by`:
  `location` (fetched whole), `stream` (read in parts) or `package` (`:95`). There is no bbox or box query in the format.
- A digest is allowed on a stream only for single-file forms read in parts (`cog`, `copc`) (`:57`). When parts are read,
  the operator is told the digest was not checked (`:58`). A whole read is used only if its digest matches (`:59`).
- Consequence: the kernel service can read points by box only if the DP serves the cloud as `copc` (or `ept`) by
  `stream`. A `las`/`laz` dataset is reached whole. The DP's actual offering is unknown (no DP service exists to read).

### 9.3 Conformance requirements for the kernel service (Q-15)
Operaflow rules bind "the supporting application" (125 rules state `THE supporting application SHALL`). Below are the
rules the kernel service must meet **if it reads datasets, saves results or sends records itself**. Rules about showing
things to the operator (open, work, checklist, offline package) bind the 3DQM client. All paths are
`OF format/specification/`; ids are the rule ids.

A. **Versions and authenticity** - before acting on any document or record:
`versions.md:34-41` (`format-version-read-first`, `unsupported-major-not-acted-on`, `unsupported-pre-release-not-acted-on`
- a pre-release such as `1.0.0-rc.1` is accepted only by its exact version, `later-minor-unknown-set-aside`,
`bad-format-version-not-acted-on`); `authenticity.md:13-14` (`signed-told-by-members`, `no-reserialization`), `:19`
(`key-set-fresh`, JWK Set at most 24 h old), `:25-27` (`verify-before-acting`, `unverified-not-acted-on`).

B. **Data access** - reading CityJSON and point clouds:
`data-and-access.md:10` (`load-in-form`), `:12` (`role-read-over-key`), `:14` (`offset-added`), `:17` (`unknown-form-set-aside`),
