## 1. Назначение и границы

**Назначение.** Оператор открывает здание из готового LOD2-набора, исправляет геометрию крыши и оболочки по облаку точек, доводит до валидного Solid и экспортирует в CityJSON.

**Входит в первый релиз (P0):**
- преобразование CityJSON → редактируемая каноническая модель с RTG;
- редактирование крыши, стен, контура, высот, надстроек (раздел 6);
- привязка к облаку точек, heatmap, plane fit (раздел 7);
- Undo/Redo, версии, baseline;
- валидация, QC-статусы, пакеты зданий, три роли;
- экспорт CityJSON только для `VALID_SOLID`.

**Не входит (исключено из продукта до отдельного решения):** налоговые метрики и отчёты (F-53 в части профилей, F-70), стерео и снимки (F-03, F-44–F-49, M-04, M-05), текстуры (F-46, F-47), построение зданий с нуля (C-01–C-04, C-06–C-18), шаблоны R-05–R-20, CityGML/OBJ/DXF/SHP/3DCityDB (F-67–F-69), скрипты и ноды (F-63, F-64), BCF (F-73), внешние API (F-71), real-time совместное редактирование (F-72).

**Отложено в P1:** пакетные операции (F-62), правила автопроверки (F-65), BuildingPart split (F-35), проёмы (F-38), вырезы и ступени (F-26–F-28), симметрия (F-32), сравнение с кадастром (F-59), многовидовой режим (F-12), QuickSlice (F-11).

## 3. Архитектура

```text
Браузер (three.js)                        Сервер
┌──────────────────────────┐   команды   ┌─────────────────────────────┐
│ editor/  инструменты,    │ ──────────▶ │ api/     auth, пакеты, lock │
│          state machine,  │             │ kernel/  B-Rep, RTG, решатель│
│          snapping, ghost │ ◀────────── │          (компилируемый)     │
│ scene3d/ (существующий)  │   патчи     │ import/  CityJSON → модель   │
└──────────────────────────┘             │ validate/ быстрый + val3dity │
                                         │ storage/ версии, журнал      │
                                         └─────────────────────────────┘
```

- **Единственный источник геометрии — сервер.** Клиент не содержит решателя, пересечений плоскостей и Boolean.
- **Ghost** — визуальная подсказка во время перетаскивания: клиент двигает только выбранную ручку и рисует её след. Ghost не обещает итоговой формы.
- **Server PREVIEW** — команда с `phase: PREVIEW`; возвращает точный diff. Оператор подтверждает именно его. `Enter` недоступен, пока нет актуального server PREVIEW.
- **COMMIT** принимает `previewId`; сервер применяет ровно тот результат, что был показан, либо отклоняет при смене версии.
- Во время перетаскивания клиент запрашивает PREVIEW с ограничением частоты (не чаще 10 запросов/с, устаревшие ответы отбрасываются).
- Язык ядра (Rust или C++) и библиотека Boolean — ADR-001, решается spike (раздел 13, G0).

## 4. Модель данных

Основа — DTO Приложения B.2 v0.2 со следующими изменениями.

**4.1. Геометрическая модель: опорные поверхности первичны (Р-08, ред. 1 от 26.11.2026).**

Текст заменяет прежнюю редакцию §4.1. Упоминания `Face.supportPlane` в v0.3 и v0.2 читаются как «плоскость поверхности `Face.surfaceId`».

**4.1.1. Состав канонической модели.** Опорная поверхность — авторитетное определение ориентации и положения грани. Одних поверхностей недостаточно: модель независимо хранит всё перечисленное ниже.

| Что хранится | Чем представлено | V1 |
|---|---|---|
| Опорные поверхности | `Surface` (4.1.2) | Только плоскости |
| Топология | `Face`, `HalfEdge`, `Vtx`, кольца, `Shell`, `Solid` с собственными ID, не зависящими от поверхностей | B.2 v0.2 |
| Определения вершин | `Vtx.definition` (4.1.3) | Три вида |
| Геометрия рёбер | Отрезок между вершинами | Отдельно не хранится |
| Ограничения hard и soft | `Constraint` | B.2 v0.2, §4.2 |
| Исходные измерения | `Measurement3D`, baseline, `sourceRef` (4.1.5) | — |
| Параметрические зависимости | Отдельные сущности, ссылающиеся на `Surface` и `Vtx` по ID | Отсутствуют (§4.2: шаблон — одноразовый генератор) |
| Семантика | `SemanticNode`, `surfaceKind` | — |
| Происхождение | `topologyLineage`, `provenanceId`, журнал | — |

Рендер-меш и CityJSON производны от этой модели и источником геометрии не являются.

**4.1.2. Поверхности.**
- Новая сущность `Surface { id: UUID; kind: 'PLANE'; plane: Plane }`. `Face.supportPlane` заменяется на `Face.surfaceId`.
- Грани лежат на общей поверхности тогда и только тогда, когда у них один `surfaceId`. Числовое совпадение плоскостей общностью не является и ничего не влечёт.
- Общая поверхность возникает только из операций: при `SPLIT_FACE` без новой плоскости обе части сохраняют `surfaceId`. Импорт создаёт каждой грани (после шага 5 раздела 5) собственную `Surface` и поверхности разных граней не объединяет.
- Изменение `Surface.plane` действует на все грани этой поверхности. Команда, меняющая поверхность, на которой есть грани вне выбора оператора, обязана содержать `sharedSurfacePolicy: 'MOVE_ALL' | 'DETACH_TARGET'`; без него — `INVALID_PAYLOAD`. При `DETACH_TARGET` выбранные грани в той же транзакции получают новую `Surface` с копией плоскости, затем применяется изменение; отделение записывается в lineage.
- Слияние граней с разными `surfaceId` — геометрическая операция: в `MERGE_COPLANAR` команда называет ведущую грань, её поверхность сохраняется, поверхность ведомой удаляется.
- Топологические операции (`SPLIT_FACE` без новой плоскости, `MERGE_COPLANAR` граней одной поверхности, `REMOVE_COLLINEAR_VERTICES`) не меняют ни одного `Surface.plane` и ни одного ограничения: значения до и после совпадают побитово.
- Расширяемость: `Surface` — размеченное объединение по `kind`. Топология, ограничения, измерения, семантика и lineage ссылаются на поверхность только по `surfaceId` и от `kind` не зависят. Схема V1 допускает только `PLANE`; алгоритмы V1 для других видов не обобщаются.

**4.1.3. Определения вершин.** `Vtx.p` — производное значение, вычисляемое из `Vtx.definition`; напрямую не редактируется. `definingFaceIds` прежней редакции отменяется.

```typescript
type VtxDefinition =
  | { kind: 'SURFACES_3'; surfaceIds: [UUID, UUID, UUID] }           // точка пересечения трёх поверхностей
  | { kind: 'EDGE_PARAM'; anchorVertexIds: [UUID, UUID]; t: number } // p = (1−t)·p(a0) + t·p(a1), 0 < t < 1
  | { kind: 'EXPLICIT'; p: V3 };                                     // координаты хранятся
```

Вид выбирает сервер, детерминированно:
1. Среди различных `surfaceId` инцидентных граней берётся тройка с наибольшим `|det(n1, n2, n3)|` (единичные нормали); при равенстве — с лексикографически меньшими ID. Если `|det| ≥ sin(coplanarTolDeg)` — `SURFACES_3` с этой тройкой.
2. Иначе, если вершина лежит внутри прямой цепочки рёбер между двумя вершинами вида `SURFACES_3` или `EXPLICIT`, — `EDGE_PARAM` с этими вершинами как якорями.
3. Иначе — `EXPLICIT` (открытая граница черновика, вершина внутри копланарной области).

- **Устойчивость.** Определение пересматривается только в commit и только если: перестало выполняться условие его вида; изменился набор инцидентных поверхностей или исчез якорь; для `EXPLICIT` — изменилась плоскость инцидентной поверхности. Смена вида, тройки или якорей записывается в `topologyLineage`.
- **Импорт не сдвигает геометрию молча.** `SURFACES_3` и `EDGE_PARAM` назначаются, только если вычисленное положение отстоит от положения вершины после шага 3 раздела 5 не более чем на `topologySnapTolM`. Иначе вершина получает `EXPLICIT` с этим положением.
- **Пересчёт `EXPLICIT`.** Если после пересмотра вид остался `EXPLICIT`, новое `p` — ортогональная проекция прежнего на пересечение инцидентных поверхностей (плоскость или прямую).

**4.1.4. Инварианты после каждого commit.**
- **Инцидентность.** Каждая вершина каждой грани отстоит от поверхности этой грани не более чем на `planarTolM`. Нарушение — `NON_PLANAR_FACE` на грани с severity по §8.3; в `DRAFT_SOLID` унаследованное нарушение допустимо, новое commit не вносит (§6).
- **Узел.** Вершина, в которой сходятся 4+ поверхностей, не проходящих через одну точку в `topologySnapTolM`, — `INCONSISTENT_JUNCTION`; исправляется только операцией `ALIGN_JUNCTION`. Ядро такие узлы само не усредняет и не подгоняет.
- **Согласованность.** `Vtx.p` равно значению, вычисленному из `definition`; у каждой грани есть `Surface`; `Surface` без граней удаляется в той же транзакции.
- **Не решено в этой редакции.** Тройка проходит условие 1, но плохо обусловлена: при угле 1,5° между плоскостями сдвиг одной на 0,02 м смещает линию пересечения на ≈ 0,76 м. Порог, диагностику и поведение решателя определяет ADR-S (раздел 16).

**4.1.5. Степени свободы, ограничения, измерения.**
- Хранимое геометрическое состояние — это `Surface.plane`, `t` вершин `EDGE_PARAM` и `p` вершин `EXPLICIT`. Решатель и операции меняют только его; остальное вычисляется.
- Жёсткие условия не ранжируются: результат либо удовлетворяет всем hard-ограничениям и инвариантам 4.1.4, либо операция отклоняется `CONSTRAINT_CONFLICT` без изменений.
- Hard-ограничение снимают и меняют только `SET_CONSTRAINT` и `REMOVE_CONSTRAINT`. Операция, удаляющая носитель hard-ограничения, отклоняется `CONSTRAINT_CONFLICT`. При разделении и слиянии ограничения переносятся по `topologyLineage`.
- Измерения неизменяемы: реконструкция, правка и решатель не изменяют и не удаляют `Measurement3D`, baseline и `sourceRef`. Прямое применение `FIT_PLANE` к поверхности (§7) тоже сохраняет измерение `PLANE`, и запись журнала на него ссылается.
- Следствие для `MOVE_VERTEX`: перемещение вершины `EDGE_PARAM` вдоль её ребра без подвижных граней меняет только `t`. Алгоритмы C.8 и C.11 v0.2 переформулируются в терминах этого состояния до начала реализации.

**4.1.6. Контракт операции.** Для каждой `OperationKind` схема payload определяет, как из выбора оператора и режима получается `editable`. `GeometryCommandResult` для PREVIEW и COMMIT содержит:
- `editable` — сущности, хранимое геометрическое состояние которых операция вправе менять;
- `affected` — существующие сущности, у которых оно изменилось;
- `dependent` — сущности, у которых изменилось только производное (`Vtx.p`, границы граней).

Всё вне `editable` фиксировано. Обязательное условие: `affected ⊆ editable`, хранимое состояние остальных сущностей побитово неизменно; иначе отказ без изменений. Созданные и удалённые сущности описывает `topologyLineage`.

**Acceptance.** Golden-тестов на правила 4.1.2–4.1.6 в разделе 12 пока нет; их нужно добавить до G1.

## 5. Импорт CityJSON → каноническая модель (новый P0-модуль I-01)

**Вход:** `CityObject` типа `Building` (с дочерними `BuildingPart`, `BuildingInstallation`) из CityJSON, уже загруженного в систему.

**Шаги:**
1. Выбрать геометрию: наивысший LoD из диапазона 2.x; если есть `Solid` и `MultiSurface` одного LoD — брать `Solid`.
2. Применить `transform`, перевести в локальную рамку здания (double precision).
3. Слить вершины в пределах `topologySnapTolM`.
4. Для каждой поверхности подогнать плоскость (SVD); при отклонении > `planarTolM` — пометить `NON_PLANAR_FACE`, грань остаётся в модели.
5. Объединить смежные копланарные грани одного семантического типа (угол < `coplanarTolDeg`, смещение < `planarTolM`).
6. Построить half-edge: twin-пары, кольца, дыры. Ребро с одной гранью → `twinId = null`; с тремя и более → `nonManifoldGroupId`.
7. Перенести семантику (`RoofSurface`, `WallSurface`, `GroundSurface` и т. д.). Грани без семантики классифицировать по нормали: `|n.z| < 0.1` — стена; `n.z < −0.9` — основание; иначе крыша. Такие грани получают тег `SEMANTICS_INFERRED`.
8. Вывести RTG: роли рёбер по геометрии двух смежных скатов. Горизонтальное ребро, оба ската опускаются от него — `RIDGE`; наклонное выпуклое — `HIP`; вогнутое — `VALLEY`; крыша–стена горизонтальное — `EAVE`; крыша–стена наклонное — `RAKE`.
9. Вывести `Footprint` из `GroundSurface` (`sourceKind: DERIVED_FROM_GROUND`).
10. Запустить валидацию, присвоить состояние: нет ошибок → `VALID_SOLID`; замкнутая оболочка с ошибками или незамкнутая → `DRAFT_SOLID`. Оператор состояние не выбирает.
11. Сохранить неизменяемый baseline (F-08) и отчёт импорта.

**Ограничения:** ограничения (constraints) при импорте не выводятся — модель импортируется без них; оператор задаёт Fixed явно. `GeometryInstance`, `appearance`, extensions сохраняются как непрозрачные данные и возвращаются при экспорте без изменений.

**Acceptance:** GT-I1…GT-I4 (раздел 12).

## 7. Работа с облаком точек

- **Привязка:** snap `POINT_CLOUD` выбирает ближайшую к лучу курсора точку в радиусе `screenSnapPx`. Координата берётся из исходных double-данных, не из GPU-буфера.
- **Heatmap (F-48):** расстояние точка–поверхность для точек в буфере `heatmapBufferM` вокруг здания; считается на сервере, клиент получает раскраску граней и сводку: RMSE, максимум, доля точек дальше порога. Порог настраивается.
- **Plane fit (M-06):** оператор выделяет точки (прямоугольник или лассо в виде). Сервер делает робастную подгонку (RANSAC + уточнение SVD по inliers) и возвращает плоскость, число inliers, долю inliers, RMSE. Результат применяется как измерение `PLANE` либо сразу как новая `supportPlane` выбранной грани через PREVIEW/COMMIT.
- **Отказ plane fit:** меньше `planeFitMinPoints` точек или доля inliers ниже `planeFitMinInlierRatio` → `INVALID_MEASUREMENT` с числами.
- **Статус измерений:** по умолчанию soft с весом `1/σ²`; hard — только после явного Fix оператором.
- Серверу нужен доступ к исходным точкам облака вокруг здания — см. допущение Д-02.

## 8. Состояния, валидация, QC, доступ

**8.1. Переходы состояний модели.**

| Из | В | Кто и как |
|---|---|---|
| импорт | `VALID_SOLID` или `DRAFT_SOLID` | Сервер, по результату валидации |
| `VALID_SOLID` | `DRAFT_SOLID` | Оператор: команда с `targetState: DRAFT_SOLID` (например, `REMOVE_FACE`). Требуется явное подтверждение в UI |
| `VALID_SOLID` | `VALID_SOLID` | Оператор: commit без новых ошибок |
| `DRAFT_SOLID` | `VALID_SOLID` | Сервер: автоматически, когда `COMMIT_VALIDATION` без ошибок; подтверждается `FINAL_VALIDATION` |
| `VALID_SOLID` | `APPROVED` | Проверяющий после `FINAL_VALIDATION`; не может быть автором ни одной версии здания после baseline |
| `APPROVED` | `VALID_SOLID` или `DRAFT_SOLID` | Автоматически при любой правке |

`DRAFT_SURFACE` в P0 возникает только внутри `REPLACE_ROOF` до достройки оболочки и не сохраняется как итог commit.

**8.2. Режимы проверки** — по §16.2 v0.2: `FAST_PREVIEW`, `COMMIT_VALIDATION`, `FINAL_VALIDATION` (val3dity, версия фиксируется в G0). `QA_APPROVAL` = `FINAL_VALIDATION` + отметка проверяющего.

**8.3. Severity по состояниям.**

| Код | `DRAFT_SOLID` | `VALID_SOLID` |
|---|---|---|
| `OPEN_BOUNDARY`, `SHELL_NOT_CLOSED`, `NON_MANIFOLD_EDGE`, `NON_MANIFOLD_VERTEX` | WARNING | ERROR |
| `SELF_INTERSECTION`, `SHELL_ORIENTATION`, `INCONSISTENT_RING_ORIENTATION`, `INCONSISTENT_JUNCTION` | WARNING | ERROR |
| `NON_PLANAR_FACE` | WARNING | ERROR |
| `DEGENERATE_EDGE`, `DEGENERATE_FACE` | ERROR | ERROR |
| `CONSTRAINT_CONFLICT`, `INVALID_CRS` | ERROR | ERROR |
| `SEMANTIC_MAPPING_ERROR` | WARNING | ERROR |

«Новая» ошибка = issue, которого нет в предыдущей версии после сопоставления `entityIds` через `topologyLineage`.

**8.4. Экспорт.** Разрешён для `VALID_SOLID` и `APPROVED` с пройденной `FINAL_VALIDATION`. Настройка проекта `exportRequiresApproval` (по умолчанию `false`, допущение Д-03). Экспорт пакета: здания без права на экспорт пропускаются и перечисляются в отчёте.

**8.5. Роли и пакеты.**

| Действие | Оператор | Проверяющий | Админ |
|---|---|---|---|
| Просмотр назначенного пакета | да | да | да (все) |
| Редактирование, Undo/Redo, Fix/Unfix | да | нет | да |
| `RESTORE_BASELINE` | да | нет | да |
| `APPROVED` / возврат на доработку с комментарием | нет | да (не автор) | да (не автор) |
| Экспорт | нет | да | да |
| Создание пакетов, назначение, профили допусков | нет | нет | да |
| Снятие чужой блокировки | нет | нет | да |

- Пакет — именованный список `buildingId`; здание входит не более чем в один активный пакет.
- Блокировка здания берётся при открытии на редактирование, продлевается активностью, истекает через `lockTtlMin` бездействия.
- Undo отменяет только операции текущего держателя блокировки в порядке стека; чужие версии через Undo не отменяются.
