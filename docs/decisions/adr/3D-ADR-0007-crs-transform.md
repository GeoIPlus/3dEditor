# 3D-ADR-0007: CRS support - transform library, EPSG table, local ENU frame

- Status: accepted (owner, 2026-11-23, D-125). Owner answers that shaped it: D-121..D-124.
- WP: 3D-32   Questions closed: -   Opened: Q-43 (EPSG terms of use)

## Context

- [D] D-92 (changes v0.3 Д-04): geographic CRSs are supported. The kernel service converts each building into a local
  metric frame (ENU) on import and back on export; only vertices changed by an edit are converted back, untouched vertices
  keep their file coordinates (D-70, GT-I4). `INVALID_CRS` narrows to unknown or unsupported CRSs.
- [D] D-93: heights and the vertical CRS are kept as in the file, not transformed. D-06/D-07: the kernel is server-only (P4).
- [D] [3D-ADR-0002](3D-ADR-0002-kernel-package-and-remote-port.md) C1 rule 1: no I/O in the kernel; rule 2: module DAG;
  third-party code only as decided by 3D-08 (Q-01, running in parallel).
- [V] CityJSON 2.0 (`cityjson/specs` main, `specs/specs.bs`; cityjson.org is not reachable from the build container):
  `transform` is mandatory (l.65, l.1133), integer vertices are decoded as `v = vi * scale + translate` (l.1142-1144);
  `referenceSystem` is an OGC URL `http://www.opengis.net/def/crs/{authority}/{version}/{code}` and "should be" a 3D CRS
  (l.1254-1272). The spec says nothing about axis order for a geographic CRS. Owner: follow the EPSG authority order (D-122).
- [V] PROJ `proj.db` (PROJ 9.8.1, EPSG v12.029 of 2025-10-02, from the pyproj 3.8.0 wheel): of 852 non-deprecated EPSG
  geographic 2D/3D CRSs, 826 are north-first (lat, lon) and **26 are east-first** (e.g. EPSG:7034..7084). Axis order is
  per code, so it must come from data, not from a rule.
- [V] `epsg-index` 2.0.0 (ISC, 40 MB, last publish 2023-11) has the CRS kind but no axis order (WKT1 without `AXIS`,
  proj4 strings default to lon/lat), so it cannot serve D-122.
- [V] Licences read from the installed packages: `proj4` 2.23.0 MIT, its dependencies `mgrs` 1.0.0 MIT and `wkt-parser`
  1.9.0 MIT; `geographiclib-geodesic` 2.2.0 MIT; PROJ (code and data) MIT (`LICENSE_proj` in the pyproj wheel); EPSG
  dataset terms of use: **not verified** (epsg.org refused by the network policy) -> Q-43.
- [A] Heights are used as ellipsoidal heights inside the ENU frame. If the file's heights are orthometric, the geoid
  undulation is almost constant across one building, so local geometry is unaffected at mm level; the inverse uses the
  same reading, so a round trip is exact regardless.

## Options
| Option | Consequences | Risk |
|---|---|---|
| A. Own closed-form geodetic <-> ECEF <-> ENU + generated EPSG table | No runtime dependency; ~100 lines | Own numerics to maintain |
| **B. proj4js at runtime + generated EPSG table (chosen by the owner, D-121)** | General library; ready for later reprojection (point cloud) | A third-party dependency inside the P4 kernel; accuracy has to be measured (done below) |
| C. PROJ (native / WASM) | Authoritative EPSG and vertical datums | Reads `proj.db` (I/O), so only in `services/kernel`; heavy; vertical datums not needed (D-93) |
| Definitions from `epsg-index` | Ready JSON | No axis order (above); 40 MB; stale |
| **Definitions generated from PROJ `proj.db` at build time** | Axis order, unit, ellipsoid and compound components per code; versioned | Generator input is a 10 MB file not in git (provenance hash recorded) |

## Decision

1. **Library:** `proj4` pinned to exactly `2.23.0` in `packages/geo-model3d/package.json` (D-121). It converts
   geodetic <-> geocentric with explicit ellipsoid parameters (`+a`, `+rf` or `+b`); no datum shift, no grids, so no I/O.
   The ENU rotation is the standard topocentric one (`src/crs/enu.js`).
2. **CRS table:** `packages/geo-model3d/src/crs/epsg-table.json` (110 KB), generated by `tools/crs-table/generate.mjs`
   from `proj.db` of a pinned pyproj wheel; `source` carries the PROJ and EPSG versions and the `proj.db` SHA-256.
   Written: EPSG and OGC geographic 2D/3D CRSs in degrees with east/north axes and a metric ellipsoid (841); projected CRSs
   in metres with east/north axes (4262); compound CRSs whose horizontal part is one of those (357). Everything else,
   including grads, feet, geocentric and south/west-oriented axes, is `INVALID_CRS` (D-92 "unknown or unsupported").
   Accepted by the owner (D-125): non-metre projected CRSs (e.g. EPSG:2263, US survey foot) become `INVALID_CRS`. Before
   this ADR the spec did not say what happens to them, and treating feet as metres would be wrong.
3. **Axis order** (D-122): file coordinates are read in the EPSG authority order of the horizontal CRS. This applies
   to projected CRSs too (EPSG:31467 is northing-first). GT fixtures (EPSG:25832, east-first) are unaffected.
4. **Frame:** `createMetricFrame(referenceSystem, originWorld)`: projected -> translation by the origin; geographic ->
   ENU at the origin. `originWorld` is in the units and axis order of the file CRS (D-124). The building rotation
   `buildingAxisDeg` stays in `brep` (3D-09).
5. **Export** (D-70, D-123): `writeBackVertices` keeps the file integers of untouched vertices, converts changed
   vertices back, rounds them (projected: `exportRoundDecimals`; geographic: `exportRoundDecimals + 5` decimals of a
   degree for angles, `exportRoundDecimals` for heights) and quantises to the file's own `transform`. A file grid coarser
   than the rounding step is reported as `PRECISION_LOSS`.
6. **Module DAG** (amends 3D-ADR-0002 C1 rule 2): new leaf module `src/crs/`; `crs` <- `brep`, `import`, `export`.
   `crs` imports only `proj4` and its own table. It is not exported from `src/index.js` until 3D-10 / 3D-11 wire it in.
7. **Relation to 3D-08 (Q-01):** this ADR admits one third-party runtime package (`proj4`) for this module only. If the
   3D-08 kernel ADR (ADR-001) sets a rule that excludes it, Option A is the fallback with the same API and tests.

## Checks

- `packages/geo-model3d/test/crs/*.test.js` (Vitest `unit`):
  - registry: URL and short forms, axis order, compound, refusals;
  - ENU accuracy: chord vs. closed-form ECEF oracle < 1e-6 m; distances vs. GeographicLib geodesics < 1e-4 m;
    metric round trip < 1e-6 m over +-500 m;
  - round trip of `test/crs/fixtures/gt-i1-epsg4937.cityjson.json` (GT-I1 converted to EPSG:4937 by proj4's UTM
    inverse, `make-fixture.mjs`): unedited integers identical; edited vertices max 0.42 mm; projected GT-I1 identical;
    a 1e-7 deg grid gives 2.3 mm and `PRECISION_LOSS`.
- `npm run check:arch`: `crs` is inside the P4 package (kernel purity, importers, canary negative control).
- Regenerating the table: `tools/crs-table/README.md`; the `source.projDbSha256` changes only with a new pinned wheel.
