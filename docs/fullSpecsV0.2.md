# ЧАСТЬ I. ОСНОВНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Введение и архитектурная предпосылка

**Назначение документа:** структурированный перечень функций для разработки онлайн-инструмента коррекции LOD2/LOD3-моделей по облакам точек и косым аэрофотоснимкам с целью получения геометрически точных моделей для налоговой оценки. Каждая функция описана по единому шаблону: **назначение → исходные данные → действия оператора → результат → технические требования**.

**Архитектурная предпосылка v0.2:** каноническая `BuildingModel` (планарный B-Rep/half-edge, параметрические крыши, constraints, семантика и происхождение измерений). **RTG** — согласованная roof-топологическая проекция, а не альтернативный независимый source of truth. Рендеринговый треугольный mesh — производный. Изменения исполняются как атомарные транзакции с валидацией и lineage (см. §15–16 и приложения B–D).

**Ключевой принцип v0.2:** `PREVIEW` не изменяет авторитетное состояние; `COMMIT` атомарен, проверяет hard constraints и валидность целевого состояния. **Черновой ремонт исходно дефектных моделей разрешён с сохранением DRAFT**, а публикация валидного Solid и расчёт итогового налогового объёма блокируются до `FINAL_VALIDATION` и QA approval. `c(e)=2` необходимо для соответствующих замкнутых оболочек, но не достаточно для валидности Solid. Интерфейс обязан объяснять конфликт ограничений вместо скрытой правки геометрии.

**Приоритет документа:** основное функциональное описание F-01–F-75 сохранено и уточнено; новые нормативные модули C/E/M/K и приложения B–I являются обязательным уточнением контрактов. Если раннее описание противоречит формальному контракту, действует более позднее явное определение v0.2. Все непринятые проектные решения перечислены в ADR-реестре.

## Модуль 1. Импорт и управление исходными данными

### F-01. Загрузка облака точек
- **Назначение:** приём исходного облака точек для последующей привязки и корректировки модели.
- **Исходные данные:** файлы LAS/LAZ, E57, PLY, TXT/XYZ; опционально — проприетарные форматы (LiData, RWP, TZF).
- **Действия оператора:** 1) выбрать файл(ы) через drag-and-drop или файловый менеджер; 2) указать систему координат (EPSG) или подтвердить автоопределение; 3) запустить фоновую загрузку; 4) по завершении проверить статистику (число точек, bounding box, плотность точек/м²).
- **Результат:** облако точек доступно в рабочей сцене как отдельный слой с метаданными (CRS, плотность, источник).
- **Технические требования:** поддержка файлов >10 ГБ через потоковую загрузку; автоматическое построение octree/LOD-пирамиды для рендеринга; порог плотности облака является конфигурацией алгоритма/проекта, а не универсальной границей качества (значение 8 точек/м² — только один возможный ориентир).

### F-02. Загрузка исходной LOD2/LOD3-модели
- **Назначение:** приём модели, подлежащей коррекции либо использованию как основа нового построения.
- **Исходные данные:** P0: CityJSON 2.0.x; P1 adapters: CityGML 2.0/3.0, OBJ, DXF, SHP Multipatch, glTF, 3D Tiles и иные форматы после проверки потерь семантики. Нестандартные или устаревшие версии CityGML поддерживаются только через отдельные адаптеры.
- **Действия оператора:** выбрать файл; проверить CRS, vertical CRS, LOD, semantic mapping; просмотреть импортные дефекты; указать, должен ли объект открыться как DRAFT или VALID_SOLID; проверить результат.
- **Результат:** канонический `BuildingModel` и исходный read-only baseline, с RTG-проекцией для скатов; исходные face/object IDs и provenance сохраняются, насколько это возможно.
- **Технические требования:** диагностика non-planar, holes, intersections, invalid orientation; ошибки импорта не должны исключать работу с моделью в `DRAFT_SOLID`. Семантические или геометрические потери фиксируются в отчёте. Не выдумывать параметры шаблона для геометрии, которую нельзя однозначно параметризовать.

### F-03. Загрузка косых и плановых аэрофотоснимков
- **Назначение:** обеспечение стереоизмерений и текстурирования.
- **Исходные данные:** снимки (TIFF/JPEG) + метаданные: EO-параметры (X, Y, Z, ω, φ, κ), внутреннее ориентирование (фокусное расстояние, размер пикселя, principal point), опционально — GNSS/IMU.
- **Действия оператора:** 1) загрузить пакет снимков и файл метаданных; 2) подтвердить параметры камеры; 3) запустить автоматическое построение стереопар по перекрытию; 4) проверить качество привязки (визуально — совпадение с облаком точек).
- **Результат:** снимки доступны в режиме стереопросмотра и как текстуры для проецирования.
- **Технические требования:** адаптеры EO (Bingo, Pix4D, Metashape, UltraMap) с явным соглашением ω/φ/κ, axis/order/units; подбор стереопар по перекрытию, базису, углу пересечения и точности; overlap ≥60% допускается как настраиваемый предварительный фильтр, не универсальный критерий хорошей стереопары; ручная корректировка EO отслеживается как отдельная версия ориентации.

### F-04. Загрузка векторных контуров (footprints)
- **Назначение:** использовать кадастровые и геодезические контуры для создания и коррекции зданий.
- **Исходные данные:** SHP, GeoJSON, DXF, CSV с координатами; горизонтальная и, при наличии, вертикальная CRS.
- **Действия оператора:** загрузить, назначить поле ID, проверить геопривязку, привязать к Building или использовать в C-02/C-03; сравнение с моделью — F-59, регуляризация — F-39.
- **Результат:** сохранённые footprints как редактируемые/референсные контуры с source lineage.
- **Технические требования:** замкнутость, отсутствие самопересечений, поддержка holes, валидация пространственных единиц и явные правила выбора при множественных совпадениях.

### F-05. Управление слоями и рабочими наборами
- **Назначение:** раздельное отображение и управление видимостью разнородных данных.
- **Исходные данные:** загруженные слои (облако, модель, снимки, векторы).
- **Действия оператора:** 1) открыть панель слоёв; 2) включать/выключать видимость; 3) настраивать прозрачность, цвет, стиль отображения; 4) сохранять комбинации как «рабочие наборы» (например, «только крыша + облако»).
- **Результат:** настроенные рабочие наборы, переключаемые в один клик.
- **Технические требования:** сохранение состояния слоёв в проекте; поддержка до 50 слоёв без просадки FPS.

### F-06. Пакетная загрузка и фоновые задачи
- **Назначение:** обработка больших массивов данных (тысячи зданий).
- **Исходные данные:** архивы или наборы файлов.
- **Действия оператора:** 1) выбрать пакет; 2) настроить очередь (приоритеты, лимиты ресурсов); 3) отслеживать прогресс в панели задач.
- **Результат:** данные загружены и поставлены в очередь на обработку.
- **Технические требования:** фоновая обработка без блокировки интерфейса; возобновление после сбоя; журнал операций.

### F-07. Управление проектами и версиями
- **Назначение:** организация изолированных проектов, доступа и репродуцируемых версий моделей (P0).
- **Исходные данные:** проект, CRS/vertical CRS, LOD profile, tolerance и measurement profiles.
- **Действия оператора:** создать проект; задать параметры; открыть Building; просматривать версии; переходить к baseline; управлять правами.
- **Результат:** проект с авторитетными версиями канонических моделей, историей операций и снимками.
- **Технические требования:** атомарный commit; per-building optimistic version; сохранение draft-моделей; аудит и доступ только по утверждённой RBAC-политике.

### F-08. Экспорт исходного состояния (baseline)
- **Назначение:** сохранить неизменяемое исходное состояние до правок (P0).
- **Исходные данные:** imported/current BuildingModel.
- **Действия оператора:** зафиксировать snapshot и комментарий.
- **Результат:** baseline для сравнения F-58 и отката F-75.
- **Технические требования:** immutable baseline, UUID, timestamp, actor/source details; baseline не заменяет версионирование.

## Модуль 2. Визуализация и навигация

### F-09. Рендеринг облака точек с LOD
- **Назначение:** производительное отображение плотных облаков в браузере.
- **Исходные данные:** загруженное облако точек.
- **Действия оператора:** 1) выбрать режим отображения (точки, круги, кубы); 2) настроить размер и цвет (по высоте, по интенсивности, по классификации); 3) управлять плотностью через ползунок «качество/производительность».
- **Результат:** интерактивное облако с автоматическим прореживанием при навигации и полной детализацией при приближении.
- **Технические требования:** octree/streaming LOD; целевой FPS ≥30 на определённом тестовом железе при bounded visible point budget, даже если серверный dataset включает миллиарды точек; WebGL2/WebGPU после benchmark. Детальные условия — Приложение A.

### F-10. Срезы и ограничивающие боксы (Clipping)
- **Назначение:** изоляция участка работ и скрытие шума.
- **Исходные данные:** текущая сцена.
- **Действия оператора:** 1) активировать инструмент «Clipping Box»; 2) задать бокс (мышью или числовыми координатами); 3) выбрать — скрывать внутри или снаружи; 4) сохранить как именованный срез.
- **Результат:** видимая только нужная часть данных.
- **Технические требования:** до 10 одновременных боксов; срезы применяются ко всем слоям или выборочно.

### F-11. Быстрый срез с автовыравниванием UCS (QuickSlice)
- **Назначение:** мгновенное сечение и ориентация системы координат по стене или полу.
- **Исходные данные:** облако точек или модель.
- **Действия оператора:** 1) выбрать инструмент; 2) указать 1–3 точки на стене/полу; 3) подтвердить — UCS автоматически ориентируется по нормали.
- **Результат:** вид «в плане» или «в разрезе» относительно выбранной плоскости.
- **Технические требования:** точность ориентации ≤0,5°; немедленное переключение камеры.

### F-12. Многовидовой режим
- **Назначение:** одновременная работа в нескольких проекциях.
- **Исходные данные:** текущая сцена.
- **Действия оператора:** 1) выбрать раскладку (2, 3, 4 вида); 2) назначить виды (перспектива, top, изометрия, камера снимка); 3) синхронизировать навигацию.
- **Результат:** синхронизированные виды, изменения отражаются во всех окнах.
- **Технические требования:** синхронизация курсора и выделения; независимая навигация по желанию.

### F-13. Навигация и закладки
- **Назначение:** быстрое перемещение между зданиями и ракурсами.
- **Исходные данные:** координаты или выделенные объекты.
- **Действия оператора:** 1) создать закладку (Ctrl+B); 2) назвать; 3) переключаться через список.
- **Результат:** сохранённые ракурсы.
- **Технические требования:** привязка закладок к ID здания; экспорт/импорт списка.

### F-14. Отображение и настройка солнца/теней
- **Назначение:** визуальная проверка геометрии по теням.
- **Исходные данные:** координаты и дата.
- **Действия оператора:** 1) задать дату/время; 2) включить тени; 3) сравнить тень модели с тенью на снимке.
- **Результат:** визуальная валидация силуэта.
- **Технические требования:** расчёт по солнечному алгоритму; сравнение с ортофото.

### F-15. Режим «только каркас» и наложение
- **Назначение:** контроль совпадения модели с облаком.
- **Исходные данные:** модель + облако.
- **Действия оператора:** 1) включить каркасный режим модели; 2) настроить прозрачность облака; 3) визуально оценить расхождения.
- **Результат:** наглядное сравнение геометрии.
- **Технические требования:** цветовая индикация отклонений (например, heatmap расстояний).

## Модуль 3. Редактирование топологии крыши (ядро)

### F-16. Построение Roof Topology Graph (RTG)
- **Назначение:** конвертировать существующую модель в редактируемую каноническую топологию со связями скатов; **построение из облака и footprint — отдельный сценарий C-15/P1**.
- **Исходные данные:** импортированный B-Rep/CityJSON или mesh с геометрией, пригодной для классификации; для реконструкции из облака — измерения и гипотезы.
- **Действия оператора:** запустить импорт и сборку adjacency; проверить полученные roof faces/ridge/eave; выбрать сохранение DRAFT либо VALID_SOLID после проверки.
- **Результат:** `BuildingModel` и производная RTG-проекция; у смежных граней общие canonical vertices/edges, у открытых поверхностей допускаются boundary edges.
- **Технические требования:** roof-plane classification и topology weld с заданными допусками; RANSAC/region growing только в ветке cloud reconstruction; отсутствие безусловного обещания watertight для дефектного импорта; диагностика невозможных соседств; правила §15 и приложения B/C.

### F-17. Разбиение ячейки (Split Cell / Split Face)
- **Назначение:** разделить одну плоскую грань на две или более **копланарные** грани без изменения формы крыши.
- **Исходные данные:** Face ID, линия/полилиния разреза на support plane.
- **Действия оператора:** выбрать грань, начертить разрез со snapping, проверить preview и подтвердить.
- **Результат:** новые face IDs с общим canonical edge и `topologyLineage`; наружная поверхность не изменена.
- **Технические требования:** корректное разделение polygon-with-holes; сохранение граничных связей; отклонение вырожденных частей. Для **нового наклона/излома** использовать E-10 `INSERT_ROOF_BREAK`, а не F-17.

### F-18. Объединение ячеек (Merge Cells)
- **Назначение:** устранение паразитных фасетов, порождённых SGM/AI.
- **Исходные данные:** две и более смежных ячейки.
- **Действия оператора:** 1) выделить ячейки; 2) нажать «Объединить»; 3) проверить плоскость результата.
- **Результат:** одна ячейка; удалены ложные рёбра.
- **Технические требования:** проверка копланарности (допуск); отказ при несовместимости.

### F-18a. Удаление мелких фасетов (Remove Details)
- **Назначение:** массовая очистка паразитных мелких полигонов.
- **Исходные данные:** выделенная область или всё здание.
- **Действия оператора:** 1) задать порог площади (например, <0,5 м²); 2) запустить; 3) подтвердить список найденных фасетов.
- **Результат:** мелкие фасеты удалены или объединены с соседними.
- **Технические требования:** отчёт «до/после»; откат.

### F-19. Выравнивание конька (Align Ridge)
- **Назначение:** изменить или восстановить положение линии конька по измерениям и правилам геометрических ограничений.
- **Исходные данные:** ridge edge, новая 3D-линия или измерения, режим `KEEP_EAVES`, `KEEP_RIDGE`, `KEEP_PLANES`, `FIT_MEASUREMENTS`.
- **Действия оператора:** выбрать ridge, задать линию/высоту и lock-режим, увидеть preview затронутых скатов/стен, подтвердить.
- **Результат:** новые согласованные плоскости и корректная топология либо диагностический отказ при несовместимости.
- **Технические требования:** при `KEEP_PLANES` нельзя произвольно менять пересечение двух фиксированных непараллельных плоскостей; при `KEEP_EAVES` пересчитываются плоскости с сохранением Fixed; запрещён скрытый best-fit, нарушающий hard constraints. См. E-09/C.7.

### F-20. Выравнивание карниза (Align Eave)
- **Назначение:** изменить геометрию линии карниза, не нарушив заданных ограничений крыши и стен.
- **Исходные данные:** eave line + targetLine/height + режим сохранения ridge/plane/walls.
- **Действия оператора:** выбрать карниз, задать цель, просмотреть затронутые walls/roof/overhang, подтвердить.
- **Результат:** пересчитанные roof/walls или `CONSTRAINT_CONFLICT`.
- **Технические требования:** общая транзакция с Rebuild Envelope; Fixed walls/vertices не изменяются без явного unlock. См. E-09/C.7.

### F-21. Подгонка ската к общему ребру (Fit to Incident Edge)
- **Назначение:** устранить щели между импортированными несшитыми скатами и правильно восстановить соседство.
- **Исходные данные:** face/edge IDs, допустимый weld tolerance, ведущая поверхность либо measurement constraints.
- **Действия оператора:** выбрать разрыв, решить какая поверхность ведущая, проверить weld preview, подтвердить.
- **Результат:** общее canonical edge; зависимые скаты перестроены без щели.
- **Технические требования:** при уже общей B-Rep границе отсутствуют «две высоты одной вершины»; не усреднять Z без алгоритма и согласия оператора; проверка manifold. См. C.8.

### F-22. Согласование вершины при схождении ≥3 скатов
- **Назначение:** определить согласованный многоплоскостной узел по ограничениям.
- **Исходные данные:** общий junction vertex, support planes, fixed/soft constraints, tolerance.
- **Действия оператора:** выбрать узел, один из режимов `KEEP_PRIMARY_PLANE`/`REFIT_SELECTED_PLANES`, просмотреть остатки измерений, подтвердить.
- **Результат:** допустимый общий junction или мотивированный отказ.
- **Технические требования:** full 3D plane intersection/rank residual; геометрическое решение может отсутствовать; никакого молчаливого смещения Fixed-точек. См. C.9.

### F-23. Ортогональная привязка (Orthogonal Snapping)
- **Назначение:** временное задание направлений 0°/90° к выбранному UCS/опорной оси.
- **Исходные данные:** выбранная геометрия и reference axis.
- **Действия оператора:** включить ограничение; указать ось; проводить линию/перемещение; отключить отдельной командой. `Esc` отменяет активный инструмент согласно E-04.
- **Результат:** ортогональное построение с визуальным указанием выбранной оси.
- **Технические требования:** Orthogonal constraint — частный случай Universal Snapping E-02; числовые и геометрические единицы не смешиваются; snap priority и режимы override доступны UI.

### F-24. Выпрямление ячейки (Straighten Face)
- **Назначение:** удалить шумовые/коллинеарные вершины или сознательно изменить форму ската.
- **Исходные данные:** face, режим `REMOVE_COLLINEAR_VERTICES`, `ALIGN_SELECTED_EDGES` или `FORCE_RECTANGLE`.
- **Действия оператора:** выбрать режим; увидеть разницу площади/границы и затронутые соседние лица; подтвердить.
- **Результат:** корректная отредактированная грань или сообщение, что действие уничтожает значимую геометрию.
- **Технические требования:** **не** преобразовывать любой n-угольник в minimum-area rectangle по умолчанию; обеспечить topology constraints и откат. См. C.10.

### F-25. Перемещение ребра / вершины с фиксацией (Move Edge / Vertex)
- **Назначение:** точное изменение геометрии с соблюдением hard/soft constraints.
- **Исходные данные:** entityId, delta/target world-local XYZ, Fixed constraints, optional alignment axis.
- **Действия оператора:** выделить, задать перемещение мышью/численно, увидеть preview новых скатов/стен и конфликты, подтвердить либо отменить.
- **Результат:** каноническая модель с пересчитанными зависимостями; Fixed-вершины неизменны.
- **Технические требования:** полный affected-subgraph solver; no partial updates; конфликт hard constraints = отказ, а не LSQ projection Fixed. См. C.11 и E-03/E-04.

### F-26. Прямоугольный вырез (Rectangular Cut)
- **Назначение:** прямоугольное топологическое разбиение, понижение участка или создание отверстия.
- **Исходные данные:** face + contour + явно выбранный режим `SPLIT_SURFACE_ONLY`, `RECESS` или `OPENING` + depth/base constraints.
- **Действия оператора:** задать прямоугольник и числовые параметры, проверить preview полостей/внутренних граней, подтвердить.
- **Результат:** topologically correct split/recess/opening с соответствующей семантикой.
- **Технические требования:** в `OPENING` для объёмной модели обеспечить корректное оформление внутренней границы/оболочки; одни вертикальные стенки при отсутствующем дне не гарантируют Solid. См. C.12.

### F-27. Вырезание угла / сегмента ребра (Cut Edge Corner / Segment)
- **Назначение:** ступенчатые фасады крыш, скосы углов.
- **Исходные данные:** ребро/угол.
- **Действия оператора:** 1) выбрать ребро/угол; 2) указать линию реза; 3) подтвердить.
- **Результат:** угол/сегмент вырезан; смежные грани перестроены.
- **Технические требования:** сохранение watertightness; откат.

### F-28. Построение ступенчатого угла (Build Step Corner)
- **Назначение:** формирование ступенек на фасаде/крыше.
- **Исходные данные:** угол/ребро + параметры ступеньки (высота, ширина).
- **Действия оператора:** 1) выбрать угол; 2) задать параметры; 3) подтвердить.
- **Результат:** ступенчатый угол.
- **Технические требования:** параметрическая генерация; сохранение c(e) = 2.

### F-29. Расширение крыши — режим «Габарит»
- **Назначение:** изменение габарита крыши и, если задано режимом, footprint стен.
- **Исходные данные:** roof boundary, новое положение, `moveWallFootprint` boolean, hard constraints.
- **Действия оператора:** выбрать `GABARIT`, указать новые габариты, проверить diff footprint/roof/walls/volume, подтвердить.
- **Результат:** новая согласованная оболочка и обновлённые метрики.
- **Технические требования:** F-29 не тождествен F-30: правила изменения стен указываются явно; восстановление roof intersections and closure обязательно.

### F-30. Расширение крыши — режим «Свес» (Overhang)
- **Назначение:** изменить roof eave boundary независимо от фиксированного контура стен.
- **Исходные данные:** roof, wall footprint, горизонтальное или поверхностное расстояние вылета, режим углов/сопряжений.
- **Действия оператора:** выбрать границу, ввести вылет, preview roof/soffit changes, подтвердить.
- **Результат:** roof overhang и обновлённые roof metrics при неизменном footprint стен.
- **Технические требования:** тип `Overhang` — внутренний domain tag; CityGML/CityJSON mapping зависит от экспортного профиля. Не моделировать произвольную вертикальную грань как overhang по умолчанию; объём зависит от принятой методики. См. C.13.

### F-31. Сдвиг ячейки по нормали (Offset Face)
- **Назначение:** переместить плоскость ската параллельно себе, пересчитав реальные границы.
- **Исходные данные:** roof plane, signed offset along unit normal, режим fixed boundary/ridge/eave.
- **Действия оператора:** задать offset, проверить preview соседних лиц, подтвердить.
- **Результат:** новая плоскость и согласованные пересечения либо конфликт constraints.
- **Технические требования:** движение support plane не означает простого переноса независимого полигона; re-intersection of all affected boundaries обязателен.

### F-32. Симметрия плоскости (Plane Symmetry)
- **Назначение:** копировать/отразить roof component относительно явно заданной плоскости.
- **Исходные данные:** roof component / face, mirror plane, mode COPY/REPLACE/JOIN.
- **Действия оператора:** указать плоскость и режим, preview reflection and intersections, подтвердить.
- **Результат:** новые IDs/геометрия с корректным stitching либо независимый DRAFT компонент.
- **Технические требования:** отражение одной face само по себе не гарантирует watertight Solid; алгоритм join/refill применяется отдельно.

### F-33. Удаление ячейки (Remove Face / Heal)
- **Назначение:** удалить лишний скат либо восстановить некорректную область.
- **Исходные данные:** face IDs, явно выбранный режим `DELETE_FACE`, `HEAL_TO_NEIGHBOR`, `FILL_PLANAR`.
- **Действия оператора:** выбрать элементы и режим; увидеть список вариантов и последствия; подтвердить.
- **Результат:** открытый DRAFT при простом удалении или согласованно восстановленная поверхность.
- **Технические требования:** запрещено делать произвольное авто-замыкание без определённого support plane/семантики; publish VALID_SOLID only after independent validation. См. C.14.

### F-34. Выравнивание высот смежных вершин (Match Roof Elevations)
- **Назначение:** обеспечить equal-Z constraint у выбранной группы точек.
- **Исходные данные:** вершины, target Z (число/min/max/mean) и список фиксированных constraints.
- **Действия оператора:** выбрать группу, высоту, preview связанных плоскостей, подтвердить.
- **Результат:** вершины согласованы по Z без скрытого нарушения планарности либо отклонённая операция.
- **Технические требования:** constraint solver и affected subgraph; если Fixed/planarity несогласованы — `CONSTRAINT_CONFLICT`.

### F-35. Разделение здания на части (BuildingPart)
- **Назначение:** разделить здание на семантически и геометрически согласованные BuildingParts.
- **Исходные данные:** Building, плоскость/полигон разбиения, splitMappingPolicy.
- **Действия оператора:** указать границу; preview внутренних closure surfaces и отдельных объёмов; подтвердить.
- **Результат:** BuildingParts со стабильными отношениями и явно определённым владением общей границей.
- **Технические требования:** финальные part Solids валидируются независимо и на перекрытия; сохранение адресов и provenance по политике, а не автоматическим полным дублированием. См. C.15.

### F-36. Добавление дормера / слухового окна (Add Dormer)
- **Назначение:** полуавтоматическая вставка дормера с детализацией согласно выбранному LOD/profile (не объявлять любое здание с дормером автоматически LOD3).
- **Исходные данные:** участок ската (обведён оператором) + облако точек / снимки.
- **Действия оператора:** 1) обвести участок на скате; 2) выбрать тип (плоская/двускатная кровля); 3) запустить — система выполняет высотную кластеризацию + RANSAC, находит выступающие точки, вписывает параметрический примитив; 4) при необходимости скорректировать размеры; 5) подтвердить.
- **Результат:** дормер как отдельный `BuildingInstallation`; основание подрезано строго по наклону несущего ската.
- **Технические требования:** RANSAC + height clustering; параметрическая подрезка; семантика BuildingInstallation; проверка watertightness.

### F-37. Добавление трубы / вентшахты (Add Chimney)
- **Назначение:** вставка трубы/вентшахты с детализацией согласно выбранному LOD/profile.
- **Исходные данные:** участок ската + облако/снимки.
- **Действия оператора:** 1) указать точку на скате; 2) выбрать тип (параллелепипед, цилиндр); 3) задать размеры (или взять из облака автоматически); 4) подтвердить.
- **Результат:** труба как `BuildingInstallation` с подрезкой основания по скату.
- **Технические требования:** автоматическое определение высоты по облаку; семантика; watertightness.

### F-38. Добавление проёма (окно/люк)
- **Назначение:** создать геометрический проём или семантическое Window/Door в целевой поверхности.
- **Исходные данные:** host face, контур, depth/reveal, выбранный режим `SEMANTIC_ONLY`, `SURFACE_HOLE`, `SOLID_RECESS`.
- **Действия оператора:** построить контур и тип, проверить preview, подтвердить.
- **Результат:** корректно оформленный объект/отверстие и назначенная семантика.
- **Технические требования:** различать отверстие в одной поверхности и полностью замкнутую объёмную конструкцию; target LOD и экспортный mapping задаются профилем.

## Модуль 4. Редактирование элементов здания (стены, контуры, высоты)

### F-39. Редактирование контура здания (Footprint Regularization)
- **Назначение:** приведение контура к корректной форме.
- **Исходные данные:** контур здания.
- **Действия оператора:** 1) выбрать контур; 2) запустить «Регуляризация» — система спрямляет близкие к прямым участки и удаляет шумовые вершины; внутренние дворы/отверстия сохраняются, если оператор явно не разрешил их удалить; 3) проверить preview и доработать вручную.
- **Результат:** регуляризованный контур без потери значимых внутренних колец; при неортогональном здании ортогонализация необязательна.
- **Технические требования:** допуск на спрямление (по умолчанию 5°); отчёт об изменениях.

### F-40. Выравнивание стен (Wall Alignment)
- **Назначение:** подгонка вертикальных плоскостей стен под облако/новую линию карниза.
- **Исходные данные:** стена + опорная линия или облако.
- **Действия оператора:** 1) выбрать стену; 2) указать опорную линию (по облаку/снимку); 3) подтвердить.
- **Результат:** стена выровнена; примыкающие крыша/пол перестроены.
- **Технические требования:** сохранение watertightness; пересчёт eave height.

### F-41. Изменение высотных отметок (Base / Eave Height)
- **Назначение:** корректировка базовой отметки или высоты карниза.
- **Исходные данные:** здание + новое значение.
- **Действия оператора:** 1) выбрать параметр (base/eave); 2) ввести новое значение (или взять из облака); 3) подтвердить.
- **Результат:** отметка изменена; объём пересчитан.
- **Технические требования:** автоматический пересчёт объёма и площади; отчёт.

### F-42. Перемещение здания как единого объекта
- **Назначение:** устранение систематического сдвига модели относительно кадастра.
- **Исходные данные:** здание + вектор смещения.
- **Действия оператора:** 1) выделить всё здание; 2) задать смещение (X/Y/Z, число); 3) подтвердить.
- **Результат:** здание сдвинуто; внутренняя структура сохранена.
- **Технические требования:** сохранение watertightness; пересчёт координат.

### F-43. Поворот здания
- **Назначение:** коррекция ориентации.
- **Исходные данные:** здание + ось и угол.
- **Действия оператора:** 1) выбрать ось; 2) задать угол; 3) подтвердить.
- **Результат:** здание повёрнуто.
- **Технические требования:** сохранение watertightness.

## Модуль 5. Работа с косыми снимками и стерео

### F-44. Режим «3D-модель + стереоизображение»
- **Назначение:** одновременный показ модели, облака и стереопары.
- **Исходные данные:** модель + стереопара + EO-параметры.
- **Действия оператора:** 1) выбрать стереопару; 2) включить стереорежим (анаглиф/полярные очки); 3) работать в 3D-виде.
- **Результат:** синхронизированный просмотр; изменения геометрии сразу видны на стерео.
- **Технические требования:** синхронизация камер; поддержка passive/active stereo.

### F-45. Стереоизмерение («плавающая марка»)
- **Назначение:** определить 3D-точку по стереопаре с количественной оценкой неопределённости.
- **Исходные данные:** минимум два снимка, IO/EO, модель дисторсии и исходные изображения.
- **Действия оператора:** выбрать пару, измерить соответствующие image coordinates, проверить residual и угол пересечения, сохранить Point3D для инструментов построения/редактирования.
- **Результат:** `Measurement3D` с XYZ, CRS, ссылками на image observations, residuals/quality.
- **Технические требования:** исходное «≤2 px» — критерий измерения на изображении, а не гарантированной точности X/Y/Z; пороги должны задаваться по camera setup и error budget (M-04).

### F-46. Проецирование текстур со снимков
- **Назначение:** автоматическое наложение текстур.
- **Исходные данные:** модель + снимки + EO.
- **Действия оператора:** 1) выбрать грани; 2) запустить «Проецировать»; 3) при необходимости выбрать снимок вручную (при конфликтах).
- **Результат:** текстурированная модель.
- **Технические требования:** выбор лучшего снимка по углу и разрешению; blending на стыках.

### F-47. Ручная корректировка текстуры
- **Назначение:** замена/уточнение текстуры на отдельных гранях.
- **Исходные данные:** грань + новый снимок.
- **Действия оператора:** 1) выбрать грань; 2) выбрать снимок; 3) настроить проекцию.
- **Результат:** обновлённая текстура.
- **Технические требования:** предпросмотр в реальном времени.

### F-48. Сравнение модели с облаком (Inspection / Heatmap)
- **Назначение:** количественная оценка расхождений.
- **Исходные данные:** модель + облако.
- **Действия оператора:** 1) запустить «Сравнить»; 2) настроить порог; 3) просмотреть heatmap; 4) перейти к проблемным зонам.
- **Результат:** карта отклонений + отчёт (RMSE, max, распределение).
- **Технические требования:** расчёт расстояний point-to-surface; цветовая шкала.

### F-49. Редактирование по одиночному снимку
- **Назначение:** корректировка геометрии по снимку там, где отсутствуют надёжные точки облака.
- **Исходные данные:** изображение + EO/IO + плоскость/поверхность/известный Z либо второй снимок.
- **Действия оператора:** измерить image coordinate, выбрать 3D-support, проверить вычисленную точку/линию и confidence, подтвердить.
- **Результат:** корректная 3D-геометрия или состояние `UNDERCONSTRAINED`.
- **Технические требования:** один image click задаёт луч, а не XYZ. Никакого восстановления 3D без второго геометрического условия; учёт окклюзии и качество EO.

## Модуль 6. Семантика и атрибуты

### F-50. Назначение семантических типов поверхностей
- **Назначение:** классифицировать canonical faces и готовить совместимый экспорт.
- **Исходные данные:** face IDs, LOD profile, export mapping.
- **Действия оператора:** выбрать грани и тип `RoofSurface`, `WallSurface`, `GroundSurface`, `ClosureSurface` и иные допустимые профильные типы; при необходимости назначить внутренний tag `OVERHANG`.

- **Технические требования:** нельзя заявлять `Overhang` универсальным стандартным типом поверхности CityJSON; lossless/lossy mappings должны быть диагностируемы. См. §16.1.

- **Результат:** объекты классифицированы.
- **Технические требования:** иерархия CityGML; проверка вложенности.

### F-52. Редактирование атрибутов
- **Назначение:** ручное заполнение/корректировка атрибутов.
- **Исходные данные:** объект + список атрибутов.
- **Действия оператора:** 1) открыть панель атрибутов; 2) отредактировать значения; 3) сохранить.
- **Результат:** обновлённые атрибуты.
- **Технические требования:** валидация типов; история изменений.

### F-53. Автоматический расчёт метрик
- **Назначение:** вычислять геометрические площади, объёмы и высоты и, при наличии утверждённого профиля, проектные/налоговые показатели.
- **Исходные данные:** валидная геометрия + `MeasurementProfile` (для юридически значимых расчётов).
- **Действия оператора:** выбрать набор метрик/профиль, запустить расчёт, просмотреть источник и формулы.
- **Результат:** `footprintArea`, `roofSurfaceArea`, `geometricSolidVolume`, `eaveHeight`, `ridgeHeight` и profile-derived values с единицами, точностью и методикой.
- **Технические требования:** считать над канонической геометрией; для невалидного Solid запрещён опубликованный итоговый объём; свесы, BuildingParts и ground height отражаются раздельно; требование «≤1%» допускается только при определённом эталоне/методике измерения. См. §16.5.

### F-54. Управление адресами и внешними ссылками (xAL)

- **Исходные данные:** xAL-атрибуты.
- **Действия оператора:** 1) проверить/отредактировать; 2) подтвердить.
- **Результат:** адреса сохранены.
- **Технические требования:** соответствие xAL; сохранение при Split Building (F-35).

## Модуль 7. Валидация и контроль качества

### F-55. Пост-валидация геометрии
- **Назначение:** контроль геометрической корректности на стадиях preview, commit и выпуска.
- **Исходные данные:** canonical BuildingModel, targetState, tolerance profile, export profile.
- **Действия оператора:** получать диагностику в preview и после commit; исправлять ошибки; запускать `FINAL_VALIDATION` перед публикацией.
- **Результат:** структурированный ValidationReport по geometry/topology/constraint/semantic/export scopes.
- **Технические требования:** c(e)=2 для closed shell недостаточно; проверять ring orientation, planar faces, self-intersection, manifold vertices, shell closure and solid overlap. Сохранение DRAFT разрешено, выпуск `VALID_SOLID`/`APPROVED` и налоговый экспорт блокируются при errors. val3dity — независимая проверка final Solid по поддерживаемым форматам (см. §16.2).

### F-56. Проверка замкнутости (Watertightness)
- **Назначение:** проверить границы shells и Solids с точной локализацией дефектов.
- **Исходные данные:** canonical B-Rep, target state.
- **Действия оператора:** запустить сканирование, перейти к каждому boundary/non-manifold element, предложить repair workflow.
- **Результат:** список дыр, non-manifold edges/vertices, нарушения оболочки и состояния Solid.
- **Технические требования:** направленные halfEdges, twin pairs и face loop traversal; отдельная проверка геометрических самопересечений.

### F-57. Проверка планарности граней
- **Назначение:** выявление непланарных полигонов.
- **Исходные данные:** модель.
- **Действия оператора:** 1) запустить; 2) задать допуск; 3) просмотреть.
- **Результат:** список граней с отклонением > допуска.
- **Технические требования:** расчёт отклонения от плоскости; подсветка.

### F-58. Сравнение с baseline (F-08)
- **Назначение:** количественно и пространственно оценивать правки.
- **Исходные данные:** current canonical model + immutable baseline.
- **Действия оператора:** сравнить, просмотреть changed surfaces, topology lineage и метрики.
- **Результат:** diff геометрии, площадей, объёмов, семантики, списка операций.
- **Технические требования:** не путать Hausdorff/point-to-surface/RMSE, указывать методику и набор сравниваемых измерений.

### F-59. Сравнение с кадастровым контуром
- **Назначение:** выявлять несовпадения здания/footprint с внешним кадастром.
- **Исходные данные:** модель + контур F-04, приведённые к одной CRS.
- **Действия оператора:** запустить сравнение, просмотреть карту/расстояния, при необходимости исправить смещение F-42 или разделить объект F-35.
- **Результат:** отчёт с методикой и геометрическими расхождениями.
- **Технические требования:** configurable warning threshold и учёт источника контура; не сравнивать разные CRS без reprojection.

### F-60. Рабочий процесс «Проверено / Требует проверки»
- **Назначение:** управление статусами зданий.
- **Исходные данные:** объекты + статусы.
- **Действия оператора:** 1) назначить статус; 2) фильтровать по статусу; 3) экспортировать статистику.
- **Результат:** статусы сохранены; дашборд качества.
- **Технические требования:** роли (оператор/проверяющий); журнал.

### F-61. Валидатор CityDoctor (опционально)
- **Назначение:** дополнительная проверка по правилам CityDoctor.
- **Исходные данные:** модель.
- **Действия оператора:** 1) запустить; 2) просмотреть.
- **Результат:** отчёт CityDoctor.
- **Технические требования:** интеграция через API или встроенный движок.

## Модуль 11. СОЗДАНИЕ ЗДАНИЙ И КРЫШ (C-01–C-20) — НОВОЕ В v0.2

> **Нормативность:** модуль обязателен для P0 Construction. Инструменты C-XX работают как над пустым зданием, так и над редактируемой моделью после импорта. Их результат — канонические топологические объекты, а не только треугольники для визуализации.

### 11.1. Единый цикл создания

1. Оператор создаёт `Building` либо выбирает `Building` / `BuildingPart`; назначает `projectId`, `buildingId`, CRS, `workingFrame`.
2. Определяет опорный контур: вручную, из кадастра, существующей геометрии или измерений облака/стереопары. Контур может быть черновым; он не объявляется валидным Solid до построения стен и основания.
3. Определяет `baseElevation` и отдельные значения высот стен, коньков, карнизов. Оператор выбирает правило привязки геометрии к измерениям.
4. Выбирает `Roof Template` или `Free Roof Construction`; вводит измерения кликами и/или численно; система показывает визуальный preview и недоопределённые степени свободы.
5. Система решает ограничения, строит поверхности и узлы RTG, сопрягает скаты, строит стены и основание, затем выполняет инкрементальную и финальную валидацию.
6. Оператор принимает или отменяет операцию. Сохранение рабочего черновика разрешено по правилам раздела 16; статус `APPROVED` и экспорт валидного Solid — только после проверки.

**Нельзя:** молча достраивать недостающую геометрию предположениями, автоматически двигать Fixed-точки или генерировать Solids с неподтверждёнными измерительными параметрами.

| C-20 | **Convert Template to Freeform** | Параметрическая крыша | Явный переход в ручную топологию, предупреждение о потере параметричности | P1 |

### 11.3. Контракт C-02 — Draw Footprint

- **Предусловия:** активный Building, известная CRS; для 2D footprint плоскость XY/заданная опорная плоскость; для измерения по снимку — определённая модель пересечения луча с пространственной опорой.
- **Интеракция:** `click → vertex`, `Backspace → remove last`, `Enter/double-click → close`, `Esc → cancel`; доступен ввод XY/Z, режим ортогональных углов, редактирование после замыкания, выбор внешнего/внутреннего кольца.
- **Геометрия:** без дублирующего завершающего vertex ID в памяти; внешние и внутренние кольца ориентируются согласованно; минимально 3 неколлинеарные точки; запрещены самопересечения и отверстия вне внешней границы.
- **Конфликты:** при пересечении контуров показать точку и варианты Undo/Continue Editing; не «чинить» контур без подтверждения. Z для 2D контура хранится отдельно от `baseElevation`.
- **Acceptance:** создаётся footprint с устойчивыми идентификаторами, валидацией `POLYGON_VALID`, UUID ссылки на источник; `Undo` восстанавливает прежнее состояние.

### 11.4. Контракт C-04/C-12 — Generate Walls / Rebuild Envelope

- При P0 опорным является footprint стен, а **не** контур свеса. Для каждого наружного ребра footprint строится стеновая поверхность до пересечения с фактической крышей; торцевые стены могут быть неплоскими как единый полигон и должны разлагаться на допустимые планарные грани.
- Высота основания и правило `GroundSurface` выбираются явно: постоянная Z, известная 3D-линия основания или согласованная ступенчатая база. Дополнительные неровности рельефа — P1.
- Стеновая геометрия пересчитывается после `MOVE_EAVE`, `MOVE_ROOF_BOUNDARY`, `CHANGE_BASE_HEIGHT`, `CHANGE_FOOTPRINT`, если пользователь не зафиксировал противоречащие ограничения.
- Предпросмотр показывает новые и удаляемые грани. Не допускаются T-junction, нулевые грани, самопересечения или двойные внутренние стены.
- **Acceptance:** для тестового footprint 10×8 м с base=0 и eave=5 создаются 4 вертикальные боковые стеновые полосы (при прямоугольной плоской крыше), GroundSurface 80 м² и замкнутый Solid с объёмом 400 м³.

### 11.5. Контракт C-05/C-06 — Roof Template & Smart Roof

**Вход:** `footprint`, `templateId`, `measurements[]`, `constraints[]`, `parameters`, `mode = PREVIEW|COMMIT`. Для каждой 3D-точки требуется источник и система координат.

**Правило определимости (обязательно):** две диагональные точки прямоугольника **не** определяют ориентацию прямоугольника. Они допускаются в двухкликовом режиме только если существует независимо заданная локальная ось здания или направляющая; аналогично две точки с разными Z не определяют единственную односкатную плоскость без правила направления уклона/дополнительного ограничения.

**Минимальные режимы P0:**

1. `FLAT_RECT`: две противоположные точки + `footprintAxis` либо одна точка, размеры и ориентация; обе отметки крыши одинаковы или получены по явному height constraint.
2. `SHED_RECT`: две противоположные точки + `footprintAxis` + `slopeDirection = LOCAL_X|LOCAL_Y` + правило, какая сторона является верхней; альтернативно 3 неколлинеарные измеренные точки.
3. `GABLE_RECT`: footprint + направление конька + eave height + ridge height **или** угол уклона + правило симметрии. Для несимметричных скатов оператор задаёт линию конька.
4. `HIP_RECT`: footprint + eave height + pitch двух направлений или ridge geometry; вырожденный конёк должен корректно давать `PYRAMID` при соответствующих ограничениях.

**Формальные шаги:** verify inputs → resolve degrees of freedom → create analytic roof planes → clip to footprint/domain → construct shared roof topology → rebuild connected walls → validate → produce atomic transaction. При недостающих данных вернуть `UNDERCONSTRAINED_GEOMETRY` со списком неопределённых параметров, а не выдумывать значения.

**Acceptance:** стабильная модель при любом порядке обновления параметров, отсутствие щелей, гарантированно проверяемые площадь/объём, повторяемость сериализации, `Undo`/`Redo`, read-after-write. Для перехода от Preview к Commit не допускается произвольная смена высоты/оси или геометрии.

### 11.6. Контракт C-07/C-08 — Free Roof Construction

- `Draw Roof Plane`: 3 неколлинеарные точки определяют аналитическую плоскость; граница ската создаётся отдельно (полигон кликов/пересечения опорных линий). Три точки не определяют границы конечной RoofSurface.
- `Create Roof Edge`: линия из двух точек получает тег `RIDGE`, `EAVE`, `VALLEY`, `HIP` или `RAKE`, но тег сам по себе **не создаёт скат**. Линия становится hard/soft constraint для последующего построения и совместно используется инцидентными скатами.
- Положение вершины из облака может иметь Z-неопределённость. Если объект недоопределён, отображается незавершённая конструкция с DRAFT статусом, без утверждения Solid.
- `Join`: создать общие топологические вершины/рёбра, а не две визуально совпадающие несвязанные линии.
- **Acceptance:** 2 RoofSurfaces, созданные из разных измерений и объединённые по коньку, используют одну общую топологическую границу; после изменения конька не возникает разрывов.

### 11.7. Контракт C-09/C-10 — Composite Roof Assembly

1. Определить выбранные независимые roof domains и режим соединения: `INTERSECT_AND_TRIM`, `EXTEND_TO_INTERSECTION`, `KEEP_PRIMARY`, `SEPARATE_BUILDING_PARTS`.
2. Выполнить аналитическое пересечение плоскостей; определить действительные линии внутри ограниченных полигонов, включая коллинеарные, параллельные и совпадающие случаи.
3. Разрезать и обрезать поверхности с корректным учётом holes и кратных пересечений. При необходимости создавать `VALLEY`/`HIP` по геометрии и контексту; не приписывать тип по одному лишь направлению линии.
4. Выполнить topological stitching с устойчивыми IDs, обновить зависимости, walls/envelope и семантику.
5. Проверить самопересечения, отсутствие нефизичных внутренних поверхностей, manifold при попытке финализировать Solid. До коммита показать overlay «что останется/удалится/добавится».
6. **Конфликт:** `PARALLEL_PLANES`, `COINCIDENT_OVERLAP`, `ZERO_LENGTH_INTERSECTION`, `NON_MANIFOLD_JUNCTION`, `MULTIPLE_SOLUTIONS` → не выбирать альтернативу молча; вернуть диагностируемый код и допустимые варианты.

**Acceptance:** L- и T-образное пересечение двух двускатных крыш; сформированы корректные линии ендов/хребтов, отсутствуют слепые дубли грани, валидный Solid после закрытия стен; Golden tests `GT-06`/`GT-07`.

### 11.8. Контракт C-19 — Reparameterize Roof

- Поддерживаемые параметры: `eaveZ`, `ridgeZ`, `pitchDeg`, `ridgeOffset`, `eaveOverhang`, `roofAxis`, `footprintDimensions`; у каждого шаблона собственный строго типизированный набор.
- При изменении параметра solver учитывает hard constraints. Если оператор ввёл несовместимые `ridgeZ` и `pitchDeg`, система возвращает конфликт с выбором: `unlock ridgeZ`, `unlock pitchDeg`, `cancel`.
- Подписи/ID граней сохраняются, если элемент однозначно продолжает существовать. При split/merge возвращается `topologyLineage` old IDs → new IDs для комментариев, измерений и выделения.
- **Acceptance:** после изменения eave/ridge Z правильные стены/скаты и метрики автоматически пересчитаны; семантические атрибуты не теряются; глобальный откат восстанавливает и параметры, и геометрию.

| R-07 | Mansard — мансардная | Footprint + два уклона + линия излома + высоты | P1 |

| R-09 | Saltbox — асимметричная двускатная | Gable + смещение ridge + раздельные уклоны | P1 |

### 12.1. Общий контракт шаблона

```typescript
interface RoofTemplateDefinition {
  id: string;                         // R-01...R-20
  version: string;                    // semver
  parameterSchema: string;            // JSON Schema ref
  requiredConstraintKinds: string[];
  generator: string;                  // ID серверного алгоритма
  supportsFreeformConversion: boolean;
}
interface RoofTemplateInstance {
  id: string;
  templateId: string;
  templateVersion: string;
  hostBuildingPartId: string;
  parameters: Record<string, number | string | boolean>;
  constraintIds: string[];
  generatedEntityIds: string[];
}
```

**Требование версионирования:** изменение алгоритма генератора не должно молча пересоздавать исторические модели. Экземпляры сохраняют `templateVersion`; миграции выполняются явно и с возможностью отката.

### 12.2. Эталонные вычисления для первичных шаблонов

- Прямоугольная плоская крыша 10×8 м: площадь кровельной поверхности = **80 м²**, если свесов нет.
- Прямоугольная двускатная крыша 10×8 м, карниз Z=5 м, конёк Z=8 м, конёк вдоль стороны 10 м, симметричные скаты: `run=4`, `rise=3`, `slopeLength=5`; площадь скатов = **100 м²**; объём замкнутого Building Solid от Z=0 = `10*8*5 + (10*8*3/2) = 520 м³`.
- Односкатная крыша на том же footprint с карнизами по двум противоположным сторонам Z=5 и Z=8, уклон через ширину 8 м: площадь поверхности = `10*sqrt(8²+3²) ≈ 85.440 м²`; объём замкнутого solid = `10*8*(5+8)/2 = 520 м³`.
- Объём **свеса** не включается в footprint здания и не добавляется автоматически к `buildingTaxVolume`: конкретная методика должна задаваться `MeasurementProfile` заказчика (см. 16.5).

### 13.2. Требования к состояниям инструмента

**Состояния:** `IDLE`, `AWAIT_SELECTION`, `COLLECTING_INPUT`, `UNDERCONSTRAINED`, `PREVIEW_PENDING`, `PREVIEW_READY`, `COMMIT_PENDING`, `COMMITTED`, `FAILED`, `CANCELLED`.

- `Esc`: отменяет текущий draft; ни один исходный элемент canonical model не изменяется. `Enter`: запрашивает commit только после корректного preview либо после явного подтверждения числовых параметров.
- Переходы состояния детерминированны; смена инструмента во время `COMMIT_PENDING` запрещает отправку второй конфликтующей транзакции на то же здание.
- `Preview` имеет собственный временный `previewId`, `sourceVersion`, `affectedEntityIds`, `geometryDiff`, `diagnostics`; preview не добавляется в историю, не синхронизируется как постоянная версия.
- `Commit` принимает тот же нормализованный набор параметров, что preview; если за время preview версия изменилась, сервер возвращает конфликт и **не** переигрывает команду автоматически.
- После commit selection по возможности переносится по `topologyLineage`, камера и working set не сбрасываются.

### 13.3. E-01/E-02 — Selection & Snapping

**Режимы выбора:** single, multi, rectangle/lasso (P1), by semantic type, by building part, cycling between overlapping hits. Точные объекты определяются по canonical entity IDs, а не индексам треугольников в GPU mesh. Приоритет в P0: активный тип элемента → ближайший snap candidate → глубина; оператор может переключать совпадающие candidates.

**Обязательные snap types:** `VERTEX`, `EDGE_NEAREST`, `EDGE_MIDPOINT`, `LINE_INTERSECTION`, `PLANE`, `GRID`, `AXIS`, `HEIGHT`, `POINT_CLOUD`, `IMAGE_MEASUREMENT`. `PARALLEL`/`PERPENDICULAR` и `ORTHOGONAL` относятся к ограничениям построения.

**Координаты:** candidate хранит `sourceEntityId`, `worldPosition`, `workingPosition`, `screenDistancePx`, `worldDistanceM`, `sourceConfidence`; экранный пиксельный допуск и мировая точность — **разные параметры**. Рекомендуемые стартовые UI-параметры (не критерий геодезической точности): snap radius 8–12 px, временное отключение клавишей, настройка приоритетов.

**Acceptance:** при наложении вершины на ребро доступны оба кандидата; snapping не меняет измеренные координаты без показанного constraint; сохранение точности не зависит от разрешения экрана или масштаба камеры.

### 13.4. E-09 — Режимы изменения конька/карниза

| Режим | Fixed | Пересчитывается | Невозможность |
|---|---|---|---|
| `KEEP_EAVES` | Опорные карнизы/линии | Конёк, planes, стены по зависимости | Новый конёк несовместим с фиксированным карнизом и планарностью |
| `KEEP_RIDGE` | Положение конька (применимо к редактированию карниза) | Остальные границы/уклоны по задаче | Попытка переместить сам фиксированный ridge |
| `KEEP_PLANES` | Обе аналитические плоскости | Только линия их математического пересечения | Параллельные, совпадающие или ненужное смещение линии |
| `FIT_MEASUREMENTS` | Явно выбранные hard constraints | Плоскости и координаты с weighted residuals | Остатки превышают проектный допуск |

**Запрещено:** произвольно перемещать конёк при `KEEP_PLANES`: линия пересечения двух непараллельных фиксированных плоскостей единственна. `F-19` и `F-20` должны использовать этот контракт.

### 13.5. E-08/E-10/E-11/E-12 — Обязательные различения

- `SPLIT_FACE`: разделение одной **планарной** поверхности на две копланарные части без изменения формы. Не создаёт новый скат.
- `INSERT_ROOF_BREAK`: добавление линии излома с новым plane constraint; изменяет форму крыши, требует перестроения соседних скатов и стен.
- `TRIM`: удаляет часть грани по действительной линии пересечения; `EXTEND` меняет границу в пределах допустимого support plane; обе операции проверяют полученную топологию.
- `DELETE_FACE`: удаляет выбранную грань и оставляет `DRAFT_SURFACE` с дырой; `HEAL_TO_NEIGHBOR`: создаёт новую согласованную поверхность; `REMOVE_INSTALLATION`: удаляет объект и восстанавливает подлежащий скат.
- `REPAIR_JUNCTION`: может менять соседние плоскости только в явно выбранном режиме soft/keep-fixed; при несовместимости constraints возвращает ошибку, не подгоняет всё здание скрытым LSQ.

### 13.6. E-06 — Undo/Redo и история

- Каждое действие `COMMIT` атомарно и имеет `operationId`, `commandId`, `beforeVersion`, `afterVersion`, `actorId`, `timestamp`, `input`, `affectedEntityIds`, `forwardPatch`, `inversePatch`, `validationSummary`, `topologyLineage`.
- Undo/Redo — **новые версии** в истории, а не изменение уже выданного номера версии; запрет удалять журнал аудита при откате.
- Должно работать для P0 creation/editing/semantics, не только F-19–F-25. Для сложных операций, где inverse patch опасен, разрешён контролируемый full snapshot.
- Клиент отображает не менее последних 50 локально доступных операций (продуктовое требование P0); серверная политика хранения/архивирования версий задаётся проектом отдельно.
- Undo чужого параллельного изменения запрещён без политики владения/локинга (раздел 16.6).

**Модель данных измерения:**

```typescript
interface Measurement3D {
  id: string;
  geometry: { kind: 'POINT' | 'LINE' | 'PLANE'; coordinates: number[][] };
  sourceType: 'POINT_CLOUD' | 'STEREO' | 'IMAGE' | 'MODEL' | 'MANUAL';
  sourceId: string | null;
  horizontalCrs: string;
  verticalCrs: string | null;
```

**Правило F-49:** одна точка на одном снимке задаёт луч, а не уникальную 3D-координату. Редактор обязан потребовать плоскость пересечения/поверхность/известную отметку/второй снимок либо перейти в `UNDERCONSTRAINED`.

## Модуль 15. ГЕОМЕТРИЧЕСКОЕ ЯДРО И ПРАВИЛА ИЗМЕНЕНИЙ (K-01–K-14) — НОВОЕ

### 15.1. Ключевые архитектурные решения

**Source of truth:** каноническая сериализуемая `BuildingModel` включает геометрию оболочек (планарный B-Rep/half-edge), параметры крыш, constraints, semantic hierarchy и происхождение измерений. `RTG` — обязательное **согласованное представление связей скатов**, а не отдельное независимо мутируемое хранилище. Рендеринговая треугольная сетка и экспорт CityJSON/CityGML являются производными. Ни один UI-компонент не меняет вершины GPU mesh вместо canonical objects.

**Владение изменениями:** каждый mutation проходит через `GeometryTransaction` и выдаёт одну версию канонической модели; граф зависимостей инкрементально пересчитывает affected elements. Все ID имеют стабильное значение в пределах сущности, а split/merge возвращают `lineage`.

| ID | Требование | Priority |
|---|---|---|
| K-01 | Единственная каноническая версия `BuildingModel` | P0 |
| K-02 | Planar B-Rep с поддержкой внутренних колец и shell/solid | P0 |
| K-03 | RTG projection / adjacency и flags `RIDGE/EAVE/...` | P0 |
| K-04 | Hard/soft constraints, solver, underconstraint diagnostics | P0 |
| K-05 | Affected subgraph recomputation | P0 |
| K-06 | Atomic preview/commit/cancel with optimistic version | P0 |
| K-07 | Invariants + progressive validation | P0 |
| K-08 | ID stability, topology lineage and semantic preservation | P0 |
| K-09 | Half-edge topology traversal, rings, orientation | P0 |
| K-10 | Exact/robust geometric predicates and tolerance policy | P0 |
| K-11 | Serializer with deterministic roundtrip and schema migration | P0 |
| K-12 | Robust polyhedral Boolean intersection/union/difference | P0 (ограниченный набор) |
| K-13 | Measurement adapters independent of kernel | P0 |
| K-14 | Real-time metrics invalidation and recomputation | P0 |

### 15.2. Геометрические ограничения

**Типы hard constraints (MVP):** `FIXED_POINT`, `COINCIDENT`, `ON_PLANE`, `PLANAR_FACE`, `SHARED_EDGE`, `HORIZONTAL`, `VERTICAL`, `PARALLEL`, `PERPENDICULAR`, `EQUAL_Z`, `FIXED_LINE`, `FIXED_EAVE`, `FIXED_RIDGE`, `ROOF_SLOPE`, `BOUNDARY_ON_FOOTPRINT`. Возможны soft constraints: `CLOSE_TO_MEASUREMENT`, `MINIMIZE_DISPLACEMENT`, `PREFERRED_AXIS`, `SYMMETRY`.

- `Hard` должны соблюдаться в конфигурируемой **численной толерантности**, а не приближаться «в среднем». При конфликте сервер возвращает `CONSTRAINT_CONFLICT` и минимально полезный список конфликтующих IDs.
- `Soft` оптимизируются по явно заданным весам и измерительной неопределённости; возвращаются residuals и solver status.
- Нормаль плоскости нормирована; для вертикальных плоскостей `solveZ(x,y)` может быть неопределён. Алгоритмы общего назначения решают трёхмерные пересечения, а `z=f(x,y)` разрешено лишь для `|normal.z| > epsilon`.
- Подгонка плоскости LSQ/SVD **не** гарантирует фиксацию hard constraints. После best-fit обязательна проверка всех hard constraints, а при расхождении — fail, а не проецирование Fixed-точек.

### 15.3. Уровни корректности модели

| State | Разрешённые действия | Что требуется |
|---|---|---|
| `DRAFT_SURFACE` | Создание отдельных контуров/скатов; локальное сохранение | Валидные отдельные геометрические примитивы; допускаются открытые границы |
| `DRAFT_SOLID` | Создание/ремонт неполной оболочки; сохранение рабочего проекта | Диагностика незамкнутых рёбер; не допускается скрывать ошибки |
| `VALID_SOLID` | Выпуск геометрии, метрики, экспорт | Полная валидность Solid, внешняя нормаль, no self-intersections, orientation, shells/holes |
| `APPROVED` | Выдача заказчику/налоговый отчёт | VALID_SOLID + семантика + метрики + QC review + подтверждённый профиль измерений |

**Политика изменений:** для `VALID_SOLID` запрещается успешный commit, который вносит новые ошибки уровня `error`; для исходно дефектной модели разрешён `DRAFT_SOLID` и операции ремонта с явным изменением диагностического статуса. Нельзя блокировать любое сохранение по `c(e)≠2` — иначе невозможно сохранять шаги исправления импортированного дефектного здания. **Но экспорт как `VALID_SOLID` и `APPROVED` остаётся блокирован.**

### 15.4. Tolerance Policy

Разделять: `numericEpsilon` (численная устойчивость алгоритмов), `topologySnapTolM` (сшивка), `planarityTolM` (допуск поверхности), `measurementTolM` (качество источника), `exportTolM` (формат/округление), `screenSnapPx` (только UX). Значения `planarityTolM=0.02` и `zAlignTolM=0.01` из v0.1 — **настраиваемые профили**, не доказанная метрологическая точность продукта.

### 15.5. Нормативный pipeline операции

```text
Request → Authorize → Read sourceVersion → Parse/Validate inputs →
Resolve measurements/CRS → Build candidate on isolated copy →
Solve hard/soft constraints → Recalculate affected subgraph →
Repair/rebuild dependent envelope → Incremental geometry checks →
Full validation (on commit / finalization per policy) →
Compute diff + lineage + affected metrics → Atomic persistence →
Emit revision event → Client applies confirmed diff
```

**Failure = no partial side effects.** Команды не должны менять canonical model при ошибках в геометрии, авторизации, version mismatch, cancellation, timeout. Долгие процессы — управляемые jobs с тем же атомарным результатом.

## Модуль 16. ПРОФИЛИ КАЧЕСТВА, ПРАВА И ВЫХОДНЫЕ МЕТРИКИ — НОВОЕ

### 16.1. Профили LOD и семантики

- Профили `LOD2_BASIC`, `LOD2_DETAILED_ROOF`, `LOD3_EXTENDED` задают обязательные типы элементов, допустимую детализацию и типы геометрии; соответствие LOD определяется правилами заказчика и целевого стандарта, а не наличием одного дормера.
- `Overhang` остаётся **внутренней классификацией детали**; базовым типом CityJSON semantic surface автоматически не является. Экспортный mapping определяет допустимый стандартный тип/расширение в выбранном профиле и записывает loss/warnings.
- `RoofSurface`, `WallSurface`, `GroundSurface`, `ClosureSurface`, `Building`, `BuildingPart`, `BuildingInstallation`, `Door`, `Window` преобразуются по явной таблице versioned mapping; внутренние доменные поля сохраняются через extension/attributes, если допускает формат.

### 16.2. Режимы проверки

- `FAST_PREVIEW`: локальные invariants и диагностика затронутых элементов; для визуальной обратной связи, не подтверждает модель как валидный Solid.
- `COMMIT_VALIDATION`: инварианты canonical model, constraints, topo stitching, self-intersection для затронутого объёма, regression checks; для критичных операций — полная проверка Solid.
- `FINAL_VALIDATION`: независимая проверка валидатором (val3dity или эквивалент, в соответствии с его поддержкой формата), semantic/schema validation, внешний экспортный roundtrip.
- `QA_APPROVAL`: `FINAL_VALIDATION` + выполненный checklist с источниками измерений и допусками.

`c(e)=2` для каждой границы замкнутой 2-многообразной оболочки необходимо, но **недостаточно**; нужны oriented edge traversal, корректные rings/holes, отсутствие самопересечений, связность/вложенность оболочек и совместимость тел BuildingPart. Нормали смежных граней не обязаны быть противоположны: противоположным должно быть **направление обхода общего ребра** в ориентациях двух граней.

### 16.3. Режимы фиксации данных

`DRAFT_SAVE`: позволяет сохранять неполную/дефектную модель с версиями и флагами; `VALIDATE_AND_PUBLISH`: блокирует выпуск при error; `EXPORT_VISUALIZATION`: может допускать DRAFT только с водяным знаком/флагом невалидности и не как источник налоговых объёмов. Бинарное условие `valid/invalid` должно иметь scope (`FACE`, `SHELL`, `SOLID`, `SCHEMA`, `MEASUREMENT`, `QC`).

### 16.4. Принципы оценки качества измерений

- Каждое значение X/Y/Z и derived metric должно иметь источник либо статус `INFERRED`.
- Нельзя смешивать pixel residual, геометрическую точность облака и абсолютную CRS accuracy в один «accuracy».
- При недостаточности измерений оператор выбирает дополнительное измерение/constraint; система показывает uncertainty и ограничение применимости операции.

### 16.5. Measurement Profile для налоговой оценки

`MeasurementProfile` содержит `profileId`, `revision`, `jurisdiction`, `units`, `footprintRule`, `roofAreaRule`, `volumeBoundaryRule`, `groundHeightRule`, `eaveHeightRule`, `overhangTreatment`, `buildingPartAggregation`, `roundingRule`, `requiredAccuracy`, `qcChecks`. Без утверждённого профильного расчёта функция F-53 считает только **геометрические** метрики, не объявляя их юридически применимыми налоговыми площадями/объёмами.

### 16.6. Multi-user и версии

- P0: project-level RBAC, per-building edit lease (временная блокировка) или сериализация операций с optimistic locking; read-only режим для остальных операторов на редактируемом здании. Сложный real-time CRDT merge 3D топологии **не входит в MVP**.
- `409 VERSION_CONFLICT`: вернуть актуальную версию/изменения; автоматическая повторная попытка возможна только после явной повторной валидации намерения оператора.
- Все входы (включая загрузки LAS/GML/E57) ограничиваются квотами, проверкой формата, безопасной обработкой ZIP/XML, проектной изоляцией, аудитом и контролем доступа.

# ЧАСТЬ II. НОРМАТИВНЫЕ ТЕХНИЧЕСКИЕ ПРИЛОЖЕНИЯ v0.2

## Приложение A. Технологический стек: исходный выбор и архитектурные ограничения

**Сохранено из v0.1:** Python backend; `numpy`/`scipy` для математики; `shapely` для 2D-контуров; `open3d` для облаков; `trimesh` как утилита для треугольных mesh/диагностики; `pyproj`/GDAL для CRS; `val3dity` для независимой проверки; TypeScript + `three.js`, Potree (после проверки совместимости), Zustand, HTTP/WebSocket.

## Приложение B. Канонические контракты данных — ЗАМЕНЯЕТ приложение B v0.1

### B.1. Ключевое исправление v0.1

Схема `RTGEdge.faces: [string,string]` **не применима к незамкнутым черновикам**: у границы открытого RoofSurface только одна инцидентная грань. Две грани на физическом ребре требуются при валидации **конкретной замкнутой оболочки**, а не при создании каждой крыши. В v0.2 RTG и B-Rep имеют явные состояния и half-edge структуру. Кроме того, геометрический `Overhang` классифицируется внутренним тегом, а не универсальным стандартным типом CityJSON Surface.

### B.2. TypeScript DTO (нормативный минимальный каркас)

```typescript
type UUID = string;
type V3 = [number, number, number]; // local working frame, metres
type V2 = [number, number]; // local horizontal coordinates, metres
interface Footprint {
  id: UUID;
  buildingPartId?: UUID;
  outerRing: V2[];         // unique coordinates; implicit closing segment
  innerRings: V2[][];      // courtyards/holes
  baseElevationM?: number;
  sourceMeasurementIds: UUID[];
}
interface ConstructionEntity {
  id: UUID;
  kind: 'GUIDE_LINE' | 'GUIDE_PLANE' | 'GRID_AXIS' | 'ROOF_EDGE_DRAFT';
  geometry: { points?: V3[]; plane?: Plane }; // per-kind JSON Schema
  edgeRole?: 'RIDGE' | 'EAVE' | 'VALLEY' | 'HIP' | 'RAKE';
  constraintIds: UUID[];
}

type ModelState = 'DRAFT_SURFACE' | 'DRAFT_SOLID' | 'VALID_SOLID' | 'APPROVED';
type EdgeRole = 'RIDGE' | 'EAVE' | 'VALLEY' | 'HIP' | 'RAKE' |
                'BOUNDARY' | 'CUT' | 'GENERIC';
type SurfaceKind = 'RoofSurface' | 'WallSurface' | 'GroundSurface' |
                   'ClosureSurface' | 'OuterCeilingSurface' |
                   'OuterFloorSurface' | 'Window' | 'Door' | 'Unclassified';
interface Vtx { id: UUID; p: V3; provenanceId?: UUID; }
interface HalfEdge {
  id: UUID;
  startVertexId: UUID;
  nextId: UUID;                 // same ring
  prevId: UUID;
  faceId: UUID;
  twinId: UUID | null;        // null allowed in DRAFT
  edgeRole: EdgeRole;
}
```

### B.3. Отношение RTG и B-Rep

- `RoofGraph` — проекция `BuildingModel` на roof faces и семантические roof edge roles. Он содержит ссылки на canonical `Face/HalfEdge/Vtx` IDs, вычисляемые `adjacency`, roof components, ridge/valley graph и параметрические зависимости.
- Derived `Face.area`, `Face.slope`, `isWatertight`, `volume`, normals/triangulation и status подсистемы **не принимаются как авторитетные входные значения клиента**. Они вычисляются на сервере после операции и могут кэшироваться по `modelVersion`.
- В draft отдельные half-edges имеют `twinId=null`. В finalized `Shell` для каждой неориентированной граничной пары есть два направленных half-edge с противоположным ходом, относящихся к двум faces той же оболочки. Отдельно проверяются геометрическая корректность и manifold at vertices.
- `RoofGraph` не обязан содержать все Wall/Ground faces. `Footprint` и `ConstructionEntity` существуют отдельно от B-Rep до построения тел: опорная линия C-08 не может стать `HalfEdge` без `faceId` и корректного кольца. Семантическая и объёмная модель всего здания находится в `BuildingModel`.
- Все координаты хранятся double precision; GPU отображает локальные float coordinates относительно выбранного origin. `sourceWorld` реконструируется через преобразование, без накопления погрешности редактирования.

### B.6. Жизненный цикл IDs и сериализация

- UUID создаются сервером при `COMMIT`; в preview допустимы ephemeral IDs с явным namespace и topology mapping.

## Приложение C. Формальные алгоритмы Construction & Editing — ЗАМЕНЯЕТ C v0.1

### C.0. Общий алгоритм исполнения

```python
def execute_geometry_operation(model, command):
    assert_permissions(command.actor_id, model.building_id)
    assert_version(model.version, command.expected_version)
    draft = model.clone_isolated()
    inputs = resolve_coordinates_and_measurements(command.payload, draft.frame)
    candidates = build_geometric_candidates(draft, command.operation, inputs)
    solved = solve_constraints(candidates, hard_first=True)
    if not solved.feasible:
        return failure("CONSTRAINT_CONFLICT", solved.conflicts)
    rebuild_dependencies(solved.affected_subgraph)
    report = validate_for_target_state(solved, command.target_state)
    if report.contains_new_blocking_errors:
        return failure("GEOMETRY_INVALID", report.issues)
    patch, inverse, lineage = compute_atomic_patch(model, solved)
    persist_in_transaction(model.version + 1, patch, inverse, lineage)
    return success(patch=patch, validation=report, lineage=lineage)
```

`preview` использует тот же solver и геометрию, но не выполняет persist; `FINAL_VALIDATION` может выполнять независимую внешнюю проверку и экспортный roundtrip. Тяжёлый full validator не обязан синхронно запускаться на каждом `mousemove`; проверка должна соответствовать стадии операции.

### C.1. `CREATE_FLAT_ROOF` (C-05/R-01)

**Given:** корректный footprint, `roofPlane` либо `roofZ`, разрешённые holes, `baseElevation`.

**Build:** создать аналитическую roof plane, ограничить её footprint в плане, построить roof face rings, затем `GENERATE_WALLS_BASE`. Если плоскость наклонена, это `SHED`, а не `FLAT` по профилю angle tolerance.

**Errors:** self-intersecting footprint; заданная плоскость вертикальна и не задаёт z(x,y) над всем footprint; roofZ < baseZ; нулевая площадь.

**Acceptance:** GT-01; корректная площадь roof=footprint area при горизонтальной плоскости, нет дублирования граней.

### C.2. `CREATE_SHED_ROOF` (C-05/R-02)

**Given:** ориентированный footprint; `slopeAxis` и eave heights (`zLow`, `zHigh`) либо 3 неколлинеарные roof measurements.

**Build:** решить `z(x,y)=ax+by+c` по constraints; создать roof domain над footprint; сгруппировать все roof vertices по аналитической плоскости, построить стены и GroundSurface. Если данных меньше трёх независимых условий — вернуть `UNDERCONSTRAINED_GEOMETRY`.

**Acceptance:** GT-02; корректное направление увеличения Z; roof area/volume соответствуют аналитическому эталону.

### C.3. `CREATE_GABLE_ROOF` (C-05/R-03)

**Given:** footprint, параллельные eave lines, ridge direction и x/y position, `eaveZ`, `ridgeZ` или уклон. В симметричном прямоугольнике ridge размещается по срединной линии соответствующей локальной оси.

**Build:** создать две roof planes через общую ridge line и свои eave lines; обрезать roof domains footprint; создать общий ridge topology; закрыть вертикальные и торцевые стеновые поверхности и GroundSurface.

**Acceptance:** GT-03: площадь крыши 100 м², объём 520 м³ для условий из §12.2. Fixed-eaves остаются на Z=5.

### C.4. `CREATE_HIP_ROOF` (C-05/R-04)

**Given:** footprint, eaveZ, ridge direction и ограничения уклонов/геометрии для всех 4 скатов. При неопределённой ridge length вернуть underconstraint; не угадывать автоматически по картинке.

**Build:** аналитически вычислить четыре поддерживающие плоскости; найти candidate lines/vertices пересечения; clip по footprint; проверить, что грани покрывают область без дыр/наложений; сформировать крыши и стены.

**Acceptance:** GT-04; корректные 4 ската, ridge/hips, valid closed solid.

### C.5. `SPLIT_FACE` и `INSERT_ROOF_BREAK` (F-17/E-10)

`SPLIT_FACE`: project split line to support plane, intersect with face polygon (including holes), create new faces **on exactly the same support plane**, rewire halfEdges, preserve boundary/semantics and lineage. `INSERT_ROOF_BREAK`: require a new plane/ridge constraint, change affected support planes, solve adjacency, rebuild envelope; these are separate command names.

**Errors:** line outside face; tangent producing zero area; split through hole with ambiguous components; incompatible fixed support plane.

### C.6. `MERGE_FACES` / `REMOVE_DETAILS` (F-18/F-18a)

- `MERGE_COPLANAR`: choose adjacent faces; ensure planar normals offset within tolerance, polygon union is one valid domain; shared internal boundary removed, same external boundary preserved; new face inherits semantics if compatible, otherwise request mapping.
- `MERGE_REFIT`: explicitly allow weighted refit only when operator specifies movable vs fixed entities; never do implicit fitting if fixed constraints conflict.
- `REMOVE_DETAILS`: identify candidates by area/shape/measurements, show removable/keep list, preserve semantically significant dormers/chimneys even if their footprint below threshold. Batch result transactional per building; failures isolated.

### C.7. `ALIGN_RIDGE` / `ALIGN_EAVE` (F-19/F-20/E-09)

```python
def align_roof_line(model, edge_id, target_line, mode):
    adjacent = get_adjacent_roof_faces(model, edge_id)
    if mode == "KEEP_PLANES":
        line = intersect_support_planes(adjacent)
        return trim_and_rebuild_on_line(line)  # no arbitrary target accepted
    hard = collect_fixed_constraints(adjacent)
    if mode == "KEEP_EAVES":
        hard += lock_opposite_eaves(adjacent)
    elif mode == "KEEP_RIDGE":
        hard += lock_unchanged_ridge(adjacent)  # only for ALIGN_EAVE
    elif mode != "FIT_MEASUREMENTS":
        return failure("INVALID_MODE")
    hard += constrain_selected_line(edge_id, target_line)
    solved = constrained_planar_solver(adjacent, hard)
    if not solved.feasible:
        return failure("CONSTRAINT_CONFLICT", solved.conflicts)
    return reclip_rebuild_validate(solved)
```

Нельзя вписывать `L_new` и две произвольные точки фиксированного противоположного ребра в одну `fitPlaneSVD`, затем считать планарность и Fixed выполненными: четыре точки в общем случае непланарны. Если требования геометрически противоречат друг другу — требуется отказ либо явное снятие/смягчение ограничения.

### C.8. `FIT_TO_SHARED_EDGE` (F-21)

В одной канонической B-Rep модели общее ребро имеет **одни** вершины. Операция F-21 нужна для импортированных несшитых соседних поверхностей: выбрать ведущую плоскость/ребро, переместить допустимые свободные вершины в constrained projection, выполнить topological weld и перестроить зависимые поверхности. Применение «среднего Z между двумя копиями общего ребра» после их объединения не имеет смысла. Без допуска на смещение и стратегии priority вернуть диагностическую ошибку.

### C.9. `ALIGN_JUNCTION` (F-22/E-11)

Для горизонтально не вертикальных planes можно решать least-squares систему пересечения `z_i(x,y)` при условии сохранения hard constraints. Для произвольных 3D-плоскостей используется общее линейное представление `n_i·p+d_i=0` и rank/residual check. Решение признаётся допустимым лишь при полном соблюдении hard constraints и ограничений на перемещения. При несовместимости предоставить режимы `KEEP_PRIMARY_PLANE`, `REFIT_SELECTED_PLANES`, `CANCEL`. **Никаких скрытых скачков многим вершинам.**

### C.10. `STRAIGHTEN_FACE` (F-24)

Режимы: `REMOVE_COLLINEAR_VERTICES` (топологически безопасен), `ALIGN_SELECTED_EDGES` (с ограничениями), `FORCE_RECTANGLE` (явно меняет область). Нельзя заменить произвольную непятиугольную или L-образную крышу на minimum-area bounding rectangle как обычную «починку». После перерисовки обязательно проверить неизменяемые внешние границы и соседей.

### C.11. `MOVE_VERTEX` / `MOVE_EDGE` (F-25)

Перемещение добавляет целевое положение как constraint, затем solver обрабатывает **все** инцидентные грани и зависимые стены/скаты. `FIXED_POINT` не меняется ни при каких обстоятельствах, кроме операции явного unlock. Не допускается, чтобы разные грани обладали независимыми координатами одного canonical Vertex. Проверить planar residual, edge lengths, self-intersections, semantic continuity и версии; ошибки → rollback.

### C.12. `RECTANGULAR_CUT` (F-26)

Три явных режима: `SPLIT_SURFACE_ONLY` (без отверстия и изменения объёма), `RECESS` (вырез + новое горизонтальное/наклонное дно и вертикальные боковые грани), `OPENING` (проём с топологически корректной границей; Solid должен быть корректно оформлен стенками проёма и внутренней/внешней поверхностью, если это объёмная конструкция). Удаление прямоугольника только из roof polygon и создание вертикальных боковин **без замыкающей поверхности** не даёт валидный Solid. Геометрическая и семантическая природа проёма задаётся отдельно.

### C.13. `CREATE_OVERHANG` (F-30)

Режим `PRESERVE_WALL_FOOTPRINT`: стены и площадь застройки не меняются; крыша расширяется на параметрический свес с выбранными corner/offset rules. Величина свеса задаётся **в горизонтальной проекции или по поверхности**, причём единица измерения явно обозначена. Roof planes продолжаются/перестраиваются в рамках constraints. Нижняя поверхность свеса (soffit) и фасетизация создаются только если так требует геометрический профиль — не подменять их вертикальными WallSurface автоматически. Volume / area computed по MeasurementProfile; не считать roof overhang частью налогооблагаемой площади застройки без правил юрисдикции.

### C.14. `REMOVE_FACE` / `HEAL_HOLE` (F-33/E-12)

`REMOVE_FACE`: переход в draft при открытой оболочке. `HEAL_HOLE`: оператор выбирает `COPY_NEIGHBOR_PLANE`, `FIT_MEASUREMENTS` или `FILL_PLANAR`, задаёт допустимые поправки; анализируется область и количество совместимых закрывающих вариантов. Если нет однозначного замыкания без самопересечения — отказ и запрос явного выбора. Отмена возвращает исходную модель.

### C.15. `SPLIT_BUILDING` (F-35)

После разбиения по плоскости/полигону создаются отдельные BuildingParts и корректные оболочки для каждого (если требуется Solid). Внутренняя разделительная граница получает правила представления и семантику в зависимости от выходного профиля. Запрещено удваивать наружные стены, путать внутреннюю общую границу с двумя пространственно разнесёнными или перекрывающимися объёмами. Политика присвоения адресов и внешних IDs определяется `splitMappingPolicy`.

### C.16. `ADD_DORMER` / `ADD_CHIMNEY` (F-36/F-37)

Источник measurements → determine roof attachment plane → параметрический placement/bounding → автоматический или ручной размер → Boolean/trim roof только в необходимых режимах → model installation shell → validate. `RANSAC`, `DBSCAN`, фиксированные `0.3 м`, `min_samples=20` из исходного C.7/C.8 являются **эвристикой initial proposal**, а не гарантированным восстановлением; threshold зависит от плотности, шумов и типа датчика. Отчёт содержит confidence, inliers и причину отказа.

### C.17. `IMPORT_EXISTING_MODEL_TO_RTG` (F-16)

**Два самостоятельных пути:** `(a) existing planar B-Rep/CityJSON → classify faces, reconstruct adjacency, infer roof constraints` и `(b) cloud + footprint → plane segmentation → hypothesis roof structure → operator approval → constructive solid generation`. Второй путь не может гарантировать правильную крышу из одного RANSAC: нужны гипотезы, missing-data handling и возможность ручной реконструкции.

## Приложение D. Frontend ↔ Backend Command Protocol — ЗАМЕНЯЕТ D v0.1

### D.1. Транспорт и версии

- REST: загрузки, snapshots, profiles, jobs, published exports; `GET /api/projects/{projectId}/buildings/{buildingId}/model?version=N`.
- WebSocket либо HTTP endpoint: интерактивные команды; доменная обработка одинакова. WebSocket не гарантирует идемпотентность сам по себе — сервер сохраняет результат по `commandId` в scoped idempotency store.
- Batch: отдельная очередь задач с ограничениями ресурсов и целостным commit **на уровне здания**.

### D.2. Типизированные команды


### D.4. Обработка ошибок и конкуренции

| Code | Значение | Реакция UI |
|---|---|---|
| `409 VERSION_CONFLICT` | Другой commit обновил модель | Показать diff, предложить re-preview |
| `422 UNDERCONSTRAINED_GEOMETRY` | Недостаточно измерений/constraints | Показать отсутствующие степени свободы |
| `422 CONSTRAINT_CONFLICT` | Невозможно удовлетворить hard constraints | Выделить конфликтные объекты и предложить unlock |
| `422 INVALID_TOPOLOGY` | Некорректное кольцо/манifold | Показать место ошибки, оставить оригинал |
| `422 INVALID_GEOMETRY` | Self-intersection, degenerate, impossible Boolean | Показать affected area, предложить исправление |
| `403 FORBIDDEN` | Нет прав/lease | Read-only / запрос доступа |
| `408/503 TIMEOUT` | Временный сбой | Повторить **с тем же commandId** только после проверки статуса |

- `COMMIT` идемпотентен на паре `(projectId, commandId)`; повтор даёт сохранённый результат, а не второй mutation.
- `expectedVersion` обязателен; запрещено безусловно «переприменить» конфликтующую команду к новой топологии без подтверждения.
- Если патч потерян клиентом, клиент запрашивает snapshot; сервер проверяет version/patch continuity; не выполняет частичное применение.
- `CANCEL` preview клиент выполняет локально либо серверная операция удаления ephemeral preview; canonical version не меняется.

### D.5. Контракты времени, кешей и снимков

- Preview может строиться оптимистично для перемещения мыши, но должен быть визуально обозначен как draft; окончательный результат приходит с сервера.
- Нельзя объявлять `isValidForTargetState=true` только на основании предварительной frontend-валидации.
- Сервер создаёт контрольный snapshot на defined milestones, а patch log содержит enough data для reproducibility, обратного восстановления и аудита.

## Приложение F. Golden Test Dataset и property-based invariants — ЗАМЕНЯЕТ F v0.1

### F.1. Базовые инварианты

1. **Identity:** сохраняются исходные Building/Part IDs; split/merge returns lineage; потеря ссылок на неизменённые поверхности запрещена.
2. **Topology:** half-edge `next/prev` формируют корректные кольца; `twin` симметричен; в FINAL Solid все граничные пары представлены обратными oriented halfEdges и нет dangling boundaries.
3. **Planarity:** каждая заявленная плоская грань укладывается в `planarTolM`; поддерживаются holes, нет нулевых колец.
4. **Geometry:** нет self-intersections, collapsed edges, overlaps, T-junctions, non-manifold vertices в `VALID_SOLID`.
5. **Constraints:** hard constraints соблюдены в численной точности; конфликт не вызывает частичного изменения модели.
6. **Provenance:** измеренные опорные точки не корректируются без явного согласия; источник сохраняется.
7. **Determinism:** `same model + same normalized command` даёт геометрически эквивалентный результат, несмотря на несущественную перестановку сериализованных map-полей.
8. **Transactionality:** error/timeouts/version mismatch → модель, версия и история не меняются.
9. **Undo/Redo:** Undo/Redo возвращает канонически эквивалентную геометрию, параметры, семантику, IDs и метрические значения; история версий при этом пополняется.
10. **No corrupt metrics:** расчёт объёма возможен только при валидной границе и явном MeasurementProfile; не должно быть молчаливого объёма открытого shell.
11. **Export:** импортер output-format возвращает эквивалентную семантику и геометрию в `exportTolM`; внешний валидатор успешно проверяет целевой формат.
12. **Numerics:** тесты на большие world coordinates, местное начало и near-degenerate плоскости; обработка vertical planes без деления на `normal.z≈0`.

**Исправление исходного инварианта:** нормали двух разных соседних граней не обязаны быть антипараллельными; согласованный порядок обхода общего ребра — обязательный топологический тест. «Объём не меняется при move/extend» также не является общим инвариантом; объём должен равняться эталонному геометрическому результату данной операции/профиля.

### F.3. Test fixture structure and numeric assertions

```text
fixtures/GT-03/
  input.model.json          # canonical empty Building + footprint
  command.json              # deterministic CREATE_GABLE_ROOF
  expected.metrics.json     # roofArea=100, volume=520
  expected.validation.json  # targetState VALID_SOLID; errors=[]
  expected.properties.json  # face counts/planes/roles/adjacency
  README.md                 # diagram, coordinate convention, independent math
```

Для вычислений с аналитическими эталонами (GT-01–GT-03) допускаемая погрешность площади/объёма устанавливается отдельно от топологического tolerance и контролируется в `expected.metrics.json`. Test runner обязан запускать минимум одну реализацию проверки, **независимую** от кода основной операции (аналитическая формула или внешний валидатор).

### F.4. Проверки pipeline/CI

- PR на kernel → unit + property-based + relevant Golden tests; PR на tool → contract tests + UI state test + target GT; merge в main → полный регресс P0, serialization roundtrip, val3dity для publishable assets.
- Каждое исправление geometry bug добавляет регрессионный fixture; запрещено изменять expected output ради зелёного CI без отдельного review.
- Integration E2E: создание здания → моделирование крыши → редактирование конька → undo/redo → валидация → публикация → экспорт → повторный импорт → сравнение метрик.
- QA фиксирует baseline screenshot/mesh only как вторичный визуальный артефакт; pixel-perfect screenshot не заменяет геометрических утверждений.
